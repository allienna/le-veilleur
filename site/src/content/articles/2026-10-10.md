# Vos agents écrivent le code à votre place. Qui a le droit de dire non ?

97 % du code d'une équipe, écrit par l'IA. Seize pour cent des pull requests fusionnées sans œil humain. Ce ne sont pas des hypothèses d'ici 2030, ce sont des chiffres publiés ces derniers jours par une boîte qui tourne déjà comme ça. La vraie question n'est plus « l'IA sait-elle coder ? ». C'est : qui vérifie, et sur quelle machine ?

### Écrire est devenu gratuit, répondre ne l'est pas

Un billet repéré ces derniers jours raconte le quotidien d'une équipe de 21 personnes qui enchaîne plusieurs déploiements par jour, grosses migrations incluses, avec une IA qui rédige la quasi-totalité du code [[1](https://tracking.tldrnewsletter.com/CL0/https:%2F%2Fswizec.com%2Fblog%2Fwhen-code-is-cheap-judgement-becomes-the-job%3Futm_source=tldrdev/1/010001a12060f32a-40df8a20-7f8a-4b4e-b56f-bf17094eb664-000000/aZhMxsgYsbidKzfsuTH_Y5HByX_oWS_A1tW8r2UfD3I=452)]. Ce qui ne bouge pas, c'est la responsabilité : chaque ingénieur reste celui qui signe ce qu'il met en prod. Le titre même de ce billet résume bien le glissement en cours :

> « When code is cheap, judgement becomes the job »

Écrire une fonction ne vaut plus grand-chose. Savoir si elle mérite de tourner chez un client, c'est ça qui devient rare.

### Le portique avant la revue

Problème : un agent qui affirme « mes tests passent » ne dit pas grand-chose. Il les a lancés sur sa propre machine, avec ce qu'il a installé en chemin, après avoir édité les fichiers qui l'arrangeaient — tests compris. Un billet technique détaille comment un portique automatisé rejoue chaque changement généré sur une machine vierge avant qu'un humain y jette un œil [[2](https://tracking.tldrnewsletter.com/CL0/https:%2F%2Fwithruntime.com%2Fblog%2Ftest-gate-for-agent-written-code%3Futm_source=tldrdev/1/010001a12060f32a-40df8a20-7f8a-4b4e-b56f-bf17094eb664-000000/gtnxJm-_wJuA05XPQZG2HI-CxswuGtAEntRWYzxVsgc=452)].

Il vérifie cinq choses très concrètes : que l'installation marche à froid, que la suite complète passe trois fois d'affilée (pas une fois, pour chasser les tests capricieux), qu'aucun test n'a disparu, qu'aucun n'a été discrètement désactivé, et surtout que les anciens tests passent toujours face au nouveau code. C'est cette dernière vérification qui piège l'agent qui a « corrigé le bug » en affaiblissant l'assertion qui le détectait. Comme le dit l'auteur, l'affirmation « les tests passent » est la plus faible qu'un agent puisse faire.

### Revoir le plan avant de revoir le code

D'autres outils remontent encore plus en amont : avant même que l'agent écrive la moindre ligne. Un projet open source permet d'annoter directement le plan qu'un agent propose — specs, diffs, documents — et de renvoyer les commentaires à l'agent en un clic, pour tous les assistants de code du marché [[3](https://tracking.tldrnewsletter.com/CL0/https:%2F%2Fgithub.com%2Fbacknotprop%2Fplannotator%3Futm_source=tldrdev/1/010001a12060f32a-40df8a20-7f8a-4b4e-b56f-bf17094eb664-000000/FQeVrEOhqomzMrw-c8rQTO-nCoDiHEB_OQmcry_D2R4=452)]. L'idée : repérer une mauvaise direction dans le plan coûte bien moins cher que la corriger une fois le code écrit, testé et poussé.

### Et si le vrai sujet, c'était le rayon d'action de l'agent ?

Dernier angle, complémentaire : plutôt que de vérifier ce que l'agent a produit, limiter ce qu'il peut toucher. AWS a publié ces derniers jours un sandbox open source pensé pour éviter les dégâts du mode « YOLO », quand un agent enchaîne des actions sans validation [[4](https://tracking.tldrnewsletter.com/CL0/https:%2F%2Fwww.theregister.com%2Fai-and-ml%2F2026%2F10%2F07%2Faws-launches-open-source-ai-agent-sandbox-to-prevent-yolo-mode-disasters%2F5301687%3Futm_source=tldrit/1/010001a1209bd94c-50b00a8e-1fd5-41f6-bd14-0faf19701108-000000/MJXlSdEs71lm1sOJc4lbBm7iSRHP9cyStKeNhI5iK7M=452)]. Microsoft va dans le même sens avec ses Execution Containers pour GitHub Copilot sous Windows, qui encadrent précisément l'accès aux fichiers, au réseau et aux identifiants pendant une session agentique, locale ou dans le cloud [[5](https://tracking.tldrnewsletter.com/CL0/https:%2F%2Fcommandline.microsoft.com%2Flocal-models-sandboxed-tools-github-windows%2F%3Futm_source=tldrit/1/010001a1209bd94c-50b00a8e-1fd5-41f6-bd14-0faf19701108-000000/wWhfcvK1dnP-fGxQTnskxC4B3-6R3NLATDugrG3KPjQ=452)].

Deux géants du cloud, à quelques jours d'écart, qui construisent des cages plutôt que des muselières. Ça en dit long sur où se situe le vrai risque aujourd'hui : pas dans la qualité du code produit, mais dans ce qu'un agent trop autonome peut faire sans qu'on l'ait décidé.

Portique de tests, revue du plan, sandbox d'exécution : trois réponses différentes à la même angoisse. On ne sait plus relire aussi vite qu'on génère. Alors on construit des garde-fous à la place.

Et vous, votre équipe a-t-elle déjà un de ces trois garde-fous — ou comptez-vous encore uniquement sur la vigilance humaine ?
