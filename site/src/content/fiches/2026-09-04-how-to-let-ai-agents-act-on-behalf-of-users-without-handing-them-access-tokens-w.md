## Résumé
L'article de WorkOS explique pourquoi confier directement un token d'accès OAuth à un agent IA est structurellement dangereux : l'agent traite les données non fiables (issues GitHub, pages web, PDF) avec la même autorité que les instructions du développeur, ce qui transforme tout contenu externe en vecteur potentiel de vol de credentials. Réduire les scopes ou raccourcir la durée de vie des tokens n'élimine pas le problème, car la fuite est une propriété du runtime, pas un instant précis dans le temps. La solution proposée, Relay (en accès anticipé), consiste à ne jamais exposer le token à l'agent : celui-ci envoie sa requête à WorkOS en indiquant le fournisseur et l'utilisateur concerné, et c'est WorkOS qui injecte le credential juste avant l'envoi au fournisseur tiers. Le texte insiste sur le fait que cela ne résout pas le prompt injection en soi, mais réduit drastiquement le rayon d'impact d'une compromission.

## Points clés
- Un agent IA reçoit dans la même fenêtre de contexte les instructions du développeur et n'importe quel contenu externe non fiable (ticket, page web, commentaire de code) — la frontière classique code de confiance/entrée non fiable disparaît.
- Un token OAuth détenu par l'agent peut fuiter par de multiples canaux ordinaires : logs d'observabilité, stdout/stderr, rapports d'erreur, fichiers de scratch/mémoire, ou simplement parce que l'agent est convaincu de l'exfiltrer lui-même.
- Réduire les scopes ou faire tourner (rotation) les tokens n'est qu'un pansement : les scopes OAuth sont trop grossiers pour un usage agentique, et la rotation ne fait que raccourcir une fenêtre de fuite qui peut se rouvrir.
- La solution proposée (WorkOS Relay) fait passer les appels par un proxy : l'agent envoie une requête avec sa clé API WorkOS, l'URL cible et l'ID utilisateur ; WorkOS résout, rafraîchit et injecte le vrai credential, puis renvoie la réponse du fournisseur inchangée.
- Le proxy applique des garde-fous concrets : hôtes autorisés en liste blanche, pas de suivi des redirections, suppression des en-têtes sensibles (Cookie, X-Forwarded-*), code d'erreur dédié (402 / `relay_authorization_required`) pour distinguer une autorisation manquante d'une erreur fournisseur.
- Limites assumées : le prompt injection n'est pas résolu, la clé API WorkOS elle-même reste une cible sensible dans le runtime, et les permissions restent celles du fournisseur (pas de contrôle fin par action d'agent).

## Analyse approfondie
Le raisonnement de l'article part d'un constat simple : le modèle de sécurité applicatif classique repose sur une frontière nette entre code de confiance (le serveur, écrit par l'équipe) et entrée non fiable (le corps de la requête). Toutes les défenses historiques — validation des entrées, requêtes paramétrées, encodage de sortie — vivent sur cette frontière. Les agents IA effacent cette frontière : un ticket de support, une page web scrapée, un PDF uploadé ou un commentaire de code deviennent des instructions traitées avec la même considération que le system prompt. Le code exécuté n'est donc plus seulement celui écrit par le développeur, mais ce code plus la réaction du modèle à un paragraphe de texte externe.

L'article détaille ensuite très concrètement où finit un token une fois placé dans l'environnement d'un agent : la fenêtre de contexte (dès que l'agent inspecte sa propre configuration ou débogue un appel), les arguments d'appels d'outils (loggés verbatim par les couches d'observabilité), les logs du fournisseur de modèle, stdout/stderr (une commande `curl` composée par l'agent ne sait pas masquer ses propres en-têtes), les rapports d'erreur (une requête HTTP échouée sérialise souvent ses en-têtes dans l'exception), les fichiers de scratch et les stores mémoire persistants, et enfin le chemin d'exfiltration proprement dit — un agent disposant du token et d'un accès réseau peut être incité à l'envoyer ailleurs, sans qu'aucun bug ne soit nécessaire : c'est la fonctionnalité qui marche comme prévu.

Un scénario illustre le risque : un agent qui triage des issues GitHub détient le token GitHub d'un utilisateur pour lire les dépôts et commenter. Un ticket ouvert par un tiers peut contenir, en fin de texte, une instruction adressée à l'agent (et non au développeur) lui demandant d'inclure son en-tête d'autorisation dans une requête de diagnostic vers une URL contrôlée par l'attaquant. Que le modèle obtempère dépend du modèle, du prompt et du jour — ce qui introduit une composante probabiliste dans la sécurité des credentials, un pari qu'il faut gagner à chaque fois. Et l'échec n'est pas récupérable comme une session classique : un token d'accès qui fuite est un credential porteur (bearer) pour l'API d'un tiers, valide jusqu'à expiration ou révocation, utilisable depuis n'importe où.

L'article démonte ensuite les deux réflexes habituels — réduire les scopes et raccourcir la durée de vie des tokens — en montrant qu'ils n'attaquent pas la racine du problème. Les scopes OAuth ont été conçus pour des applications, pas pour des agents : un token permettant de lire les dépôts dont un agent a besoin permet généralement de lire tous les dépôts visibles par l'utilisateur, car les scopes réels des fournisseurs se regroupent par grandes surfaces produit. La rotation, elle, réduit la fenêtre de fuite sans la fermer : un attaquant capable d'atteindre un token une fois peut généralement l'atteindre à nouveau, car le chemin de fuite est une propriété du runtime plutôt qu'un instant donné ; et un flux de refresh signifie que le runtime détient aussi le refresh token, qui vaut souvent plus que le token d'accès lui-même. Ces deux mitigations acceptent la prémisse que le token doit se trouver dans l'environnement de l'agent — c'est cette prémisse qu'il faut remettre en cause.

La solution présentée consiste à ne plus livrer le credential au code qui en a besoin, mais à laisser ce code décrire l'appel qu'il souhaite effectuer au nom d'un utilisateur donné. WorkOS propose ceci sous le nom de Relay (actuellement en accès anticipé) : l'agent envoie sa requête à WorkOS en nommant le fournisseur et l'utilisateur pour lequel il agit, et WorkOS attache le credential au moment de l'envoi. Concrètement, une requête proxifiée porte la clé API WorkOS dans `Authorization`, l'URL cible dans `X-Relay-URL`, l'ID utilisateur dans `X-Relay-User`, et `X-Relay-Organization` quand la connexion a été autorisée sous une organisation. Le fournisseur est résolu à partir de l'hôte de l'URL cible, `X-Relay-Provider` servant de surcharge optionnelle en cas d'ambiguïté. WorkOS vérifie la clé, résout le compte connecté de l'utilisateur, récupère le credential depuis le store de credentials Pipes, le rafraîchit s'il a expiré, retire ses propres en-têtes de contrôle, injecte le token du fournisseur, et retransmet la réponse du fournisseur telle quelle. Méthode, corps et en-têtes de contenu passent inchangés, de sorte que convertir un appel direct en appel proxifié revient à une simple modification d'en-têtes plutôt qu'à une réécriture.

Deux détails rendent ce mécanisme réellement utilisable plutôt que simplement sécurisé sur le papier. Le premier concerne la sémantique honnête des erreurs : un proxy pass-through a un problème de nommage — s'il renvoie son propre 401 ou 403, impossible de le distinguer du 401 du fournisseur ou d'un rejet de la clé API par le proxy. Un utilisateur n'ayant pas connecté le fournisseur, ou dont l'autorisation a été révoquée, reçoit donc un `402` avec le code `relay_authorization_required` accompagné d'une `authorization_url` vers laquelle le rediriger. Chaque réponse proxifiée porte aussi un en-tête `X-Relay-Upstream-Status`, indiquant si la requête a effectivement atteint le fournisseur — un `404` GitHub et un `404` d'un fournisseur inconnu cessent ainsi de se ressembler. Le second détail est que le token vit désormais derrière une frontière que l'agent ne peut franchir même s'il le voulait : les requêtes ne peuvent cibler que des hôtes en liste blanche pour un fournisseur supporté, les redirections ne sont pas suivies (ce qui compte plus qu'il n'y paraît, car une redirection suivie est précisément la façon dont un credential injecté finit sur un hôte que personne n'a autorisé), les en-têtes `Cookie`, `X-Forwarded-*` et les en-têtes de saut (hop-by-hop) sont retirés à l'aller, `Set-Cookie` au retour. Le délai d'attente amont est de trente secondes et les corps sont transmis octet pour octet jusqu'à 5 Mo. Résultat : un agent compromis peut effectuer des appels fournisseur qu'il ne devrait pas faire, mais il ne peut pas repartir avec un credential.

L'article prend soin de lister ce que cette approche ne résout pas. D'abord, le prompt injection reste entier : rien ici ne rend un agent meilleur pour ignorer des instructions embarquées dans les données qu'il lit ; un agent qu'on peut convaincre de poster un message Slack non désiré peut toujours être convaincu de le faire — le proxy change ce que l'attaquant peut emporter, pas sa capacité à influencer l'agent. Ensuite, la clé API WorkOS reste présente dans le runtime et authentifie tous les appels de l'environnement ; Relay ne la supprime pas, il faut donc l'injecter au moment de la requête plutôt que de la coder en dur dans du code ou des prompts visibles par l'agent, et la faire tourner si un runtime est compromis — déplacer un secret hors de portée en en laissant un autre plus puissant à disposition est un mouvement latéral, pas une amélioration. Enfin, les permissions du fournisseur restent celles du fournisseur : les appels proxifiés sont contraints par des hôtes en liste blanche, pas par ce qu'un agent donné devrait faire précisément ; l'autorisation fine des actions d'agent reste un vrai manque, et le proxy est l'endroit naturel où le combler un jour, mais son existence en tant que point de passage ne vaut pas politique d'autorisation.

Ce qu'on gagne réellement, conclut l'article, est un changement de rayon d'impact (blast radius). Un token qui fuite est une capacité durable, portable et utilisable hors ligne. Une session d'agent détournée est un processus vivant qu'on peut tuer, dont les appels transitent par un point unique où ils peuvent être observés et coupés. Ce sont deux incidents très différents, et l'un des deux se termine dès qu'on le remarque.

L'article referme sur une note plus générale : le proxying de credentials n'est pas une idée nouvelle, ce qui joue en sa faveur — les paiements y sont arrivés en premier, les coffres-forts de cartes et la tokenisation existant précisément parce que le moyen le plus rapide de réduire le périmètre d'un audit est de s'assurer que la valeur sensible n'entre jamais dans le système. Le même raisonnement s'applique aux tokens OAuth et aux runtimes d'agents, pour la même raison : on ne peut pas faire fuiter ce qu'on n'a jamais détenu. Le principe durable, indépendant de tout produit particulier, est que les credentials doivent résider dans le composant le moins accessible capable de faire le travail — or les runtimes d'agents sont aujourd'hui le composant le plus accessible dans la plupart des architectures : ils lisent du texte contrôlé par un attaquant, journalisent tout, persistent un état pour progresser, et agissent selon leurs propres conclusions. C'est un bon endroit pour prendre une décision ; c'est un mauvais endroit pour garder une clé. La question à se poser, si l'on confie aujourd'hui un token à un agent, n'est pas de savoir si le prompt est robuste, mais ce qui se passera le jour où il ne le sera pas.

## Pourquoi ça compte
À mesure que les agents IA se généralisent pour agir au nom des utilisateurs sur des API tierces, la gestion des credentials devient un angle mort de sécurité majeur et largement sous-estimé, distinct du seul sujet du prompt injection ; ce type d'architecture de délégation (proxy de credentials) est amené à devenir un standard de facto pour toute équipe déployant des agents en production.
