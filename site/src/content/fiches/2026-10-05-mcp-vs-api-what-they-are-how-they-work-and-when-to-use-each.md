## Résumé
L'article explique pourquoi Anthropic a créé le Model Context Protocol (MCP) alors que les API existent déjà depuis des décennies et couvrent déjà la quasi-totalité des besoins d'intégration logicielle. La thèse centrale est que MCP et les API ne sont pas concurrents mais répondent à des besoins différents : les API sont conçues pour des développeurs humains qui écrivent du code statique après avoir lu une documentation, tandis que MCP est conçu pour des modèles d'IA qui doivent découvrir, comprendre et invoquer des capacités de façon autonome et dynamique à l'exécution. L'article détaille le fonctionnement technique des deux approches, leurs différences structurelles (découverte vs pré-configuration, statique vs dynamique, sans état vs avec état, orienté documentation vs orienté schéma), puis donne des critères concrets pour choisir l'une ou l'autre. Il conclut que la plupart des systèmes d'IA en production combinent les deux : les API au niveau des services, MCP au niveau de la couche d'intégration IA.

## Points clés
- Une API est un contrat figé, pensé pour un développeur qui lit une documentation puis écrit du code qui appelle des endpoints connus à l'avance (REST, GraphQL, gRPC).
- MCP est un protocole ouvert, basé sur JSON-RPC 2.0, qui permet à un modèle d'IA de découvrir dynamiquement les outils, ressources et prompts exposés par un serveur, via une architecture client-serveur (MCP Host / MCP Server).
- La différence fondamentale est la découverte à l'exécution : une API suppose que l'appelant sait déjà ce qu'il peut appeler ; MCP permet à l'IA de demander « que peux-tu faire ? » et d'adapter son comportement en conséquence, sans changement de code.
- Les API REST sont sans état par conception (scalabilité horizontale) alors que les sessions MCP sont avec état, ce qui permet de maintenir un contexte (transaction ouverte, répertoire courant) sur plusieurs appels d'outils successifs.
- En pratique, la grande majorité des systèmes IA en production utilisent les deux ensemble : des serveurs MCP qui encapsulent des API REST/GraphQL/gRPC existantes pour les rendre exploitables par des agents IA.
- MCP introduit des risques de sécurité spécifiques (injection de prompt via du contenu récupéré, nécessité d'une liste blanche d'outils et du principe du moindre privilège) qui s'ajoutent aux problématiques classiques de sécurité des API.

## Analyse approfondie

### Partie 1 — Les API, le socle existant
Une API définit un contrat précis entre un fournisseur et un consommateur : quelles requêtes sont possibles, sous quel format, et quelles réponses ou erreurs en résultent. Le modèle REST associe les méthodes HTTP (GET, POST, PUT, PATCH, DELETE) à des opérations sur des ressources identifiées par des URLs, et fonctionne sans état — chaque requête est autonome, ce qui permet de répartir la charge sur n'importe quelle instance de serveur. GraphQL propose une alternative où le client précise exactement les champs et relations qu'il souhaite récupérer en un seul point d'entrée, réduisant les problèmes de sur- ou sous-récupération de données propres à REST, au prix d'une implémentation serveur plus complexe. gRPC, basé sur Protocol Buffers et HTTP/2, offre un encodage binaire compact adapté aux communications internes à forte performance entre microservices, mais n'est pas adapté aux API publiques consommées par un navigateur.

Dans tous les cas, le modèle de consommation reste le même : un développeur humain lit la documentation, comprend l'interface, et écrit un code statique qui appelle les bons endpoints avec les bons paramètres. Si l'API évolue, c'est le développeur qui doit mettre à jour son code ; si une nouvelle capacité apparaît, c'est encore à lui de l'intégrer explicitement. Ce modèle fonctionne très bien tant que le consommateur est un humain, mais devient limitant lorsque le consommateur est un modèle d'IA censé décider par lui-même, à l'exécution, de ce qu'il doit faire.

### Partie 2 — MCP, le protocole pensé pour les modèles
Lorsque les grands modèles de langage ont commencé à agir comme des agents capables d'enchaîner des actions plutôt que de simplement générer du texte, un nouveau problème est apparu : comment un agent découvre-t-il les outils disponibles, comprend-il leur usage, choisit-il le bon outil, l'invoque-t-il avec les bons paramètres, puis interprète-t-il le résultat ? L'approche initiale — décrire chaque outil manuellement dans le prompt système — fonctionnait mais ne s'adaptait pas à l'échelle : chaque application devait redéfinir ses propres outils, sans aucune standardisation ni mécanisme de découverte entre applications différentes.

Anthropic a conçu MCP pour résoudre ce problème en standardisant la façon dont une IA découvre des sources de données et des outils externes, comprend leurs capacités via une interface homogène, et les invoque avec des entrées/sorties structurées — avec l'ambition de faire pour l'usage d'outils par l'IA ce que HTTP a fait pour les API web.

MCP définit une architecture client-serveur : un **MCP Host** est l'application d'IA (un client de bureau, un IDE, un framework d'agent) qui embarque un client MCP gérant les connexions aux serveurs ; un **MCP Server** est un programme qui expose des *tools* (fonctions appelables), des *resources* (données consultables) et des *prompts* (modèles réutilisables) — par exemple un serveur de fichiers exposant read_file, write_file, list_directory, ou un serveur de base de données exposant execute_query, list_tables. Le protocole MCP lui-même, construit sur JSON-RPC 2.0, gère de façon uniforme la découverte des capacités, l'invocation d'outils, l'accès aux ressources et la restitution des résultats, quel que soit le serveur sous-jacent.

Le déroulement technique suit une séquence précise : à l'**initialisation**, le client envoie une requête initialize et le serveur répond avec ses capacités (version du protocole, outils, ressources, prompts disponibles) sans configuration préalable nécessaire ; pour la **découverte des outils**, une requête tools/list renvoie la liste structurée des outils avec leur nom, leur description en langage naturel et leur schéma JSON de paramètres, que le modèle reçoit comme du contexte ; pour l'**invocation**, le modèle génère un appel structuré (nom de l'outil + paramètres conformes au schéma) transmis via tools/call, le serveur exécute et renvoie un résultat structuré ; l'**accès aux ressources** se fait via resources/read pour des données en lecture seule (par opposition aux outils, qui réalisent des actions) ; enfin, le protocole prend en charge le **streaming** pour les opérations longues et une capacité de **sampling** permettant à un serveur de solliciter lui-même une complétion du modèle, pour des interactions multi-étapes plus complexes. Le socle JSON-RPC rend le protocole agnostique du transport : stdio pour les processus locaux, HTTP avec Server-Sent Events ou WebSockets pour les serveurs distants.

La portée stratégique de MCP vient de sa standardisation : un serveur MCP écrit une seule fois fonctionne avec n'importe quel host compatible, sans code d'intégration spécifique à chaque application. En 2026, des milliers de serveurs MCP existent déjà pour les services courants (systèmes de fichiers, bases de données, recherche web, exécution de code, GitHub, Slack, Notion, Google Drive, etc.), créant un écosystème qui grandit sur le même principe que celui des API REST : une interface standardisée fait émerger un marché d'implémentations.

### Partie 3 — Les différences fondamentales
Six axes de différenciation structurent l'article. D'abord, **le consommateur visé** : les API s'adressent à un développeur qui comprend déjà l'interface au moment d'écrire son code, alors que MCP s'adresse à un modèle qui doit comprendre les capacités à l'exécution — ce qui explique que les API optimisent l'expérience développeur (documentation claire, conventions stables) tandis que MCP optimise la compréhension machine (descriptions structurées, schémas homogènes).

Ensuite, **découverte contre pré-configuration** : avec une API, l'appelant sait d'avance ce qu'il peut appeler, car les endpoints sont codés en dur ; avec MCP, l'IA découvre dynamiquement les capacités à la connexion et peut exploiter immédiatement un nouvel outil ajouté côté serveur, sans aucune modification de code côté agent.

Troisième axe, **capacité statique contre dynamique** : une intégration API encode à l'avance la logique « si l'utilisateur fait X, appeler l'endpoint Y » ; une intégration MCP laisse le modèle décider à l'exécution quel outil utiliser selon la tâche, ce qui permet à un même agent de s'adapter automatiquement à des combinaisons de serveurs MCP différentes — un atout central pour les agents multi-étapes (rechercher, coder, tester, soumettre une pull request).

Quatrième axe, **sessions sans état contre avec état** : les API REST sont sans état par choix de conception, pour la scalabilité horizontale ; les sessions MCP sont avec état et peuvent conserver du contexte sur plusieurs appels successifs (transaction ouverte sur une base, répertoire de travail courant), au prix d'une gestion de connexion plus complexe à faire monter en charge.

Cinquième axe, **schéma contre documentation** : les API sont documentées pour des humains (specs OpenAPI/Swagger, portails développeurs), même si ces specs sont aussi lisibles par une machine ; les outils MCP sont décrits par des schémas conçus spécifiquement pour être compris par un modèle (nom, description rédigée pour l'IA, schéma JSON des entrées), livrés à l'exécution comme du contexte ordinaire plutôt que comme une documentation séparée.

Sixième axe, **profondeur contre largeur d'intégration** : une intégration API est en général profonde et taillée sur mesure pour un service donné (ex. Stripe, avec sa gestion fine des codes d'erreur et des retries) ; une intégration MCP peut être large, un agent se connectant simultanément à des dizaines de serveurs pour couvrir des tâches variées, la profondeur de chaque intégration dépendant alors de la façon dont chaque serveur expose ses capacités.

### Partie 4 — Quand utiliser quoi
L'article recommande les API pour : le développement logiciel traditionnel où un humain écrit le code d'intégration ; les cas nécessitant un contrôle fin (gestion précise des erreurs, logique de retry personnalisée, authentification complexe) ; les contraintes de performance (les appels directs, notamment en gRPC, ont moins de surcharge qu'un passage par un modèle d'IA et une couche MCP) ; les schémas d'intégration connus et figés à l'avance ; et les intégrations publiques destinées à des développeurs tiers, où MCP ne remplace pas les API publiques classiques.

Il recommande MCP pour : la construction d'agents IA devant découvrir et utiliser des outils de façon autonome ; la volonté d'une connectivité « plug-and-play » (un outil construit en serveur MCP devient immédiatement compatible avec tout l'écosystème des hosts MCP) ; les cas où l'IA doit combiner de nombreux outils de façon flexible (fichiers, code, recherche web, calendrier, email) sans code d'intégration spécifique pour chaque combinaison ; la volonté que l'agent s'adapte automatiquement à l'ajout de nouvelles capacités dans son environnement ; et les flux de travail nécessitant un état partagé entre plusieurs appels d'outils successifs.

En pratique, la plupart des systèmes IA en production en 2026 combinent les deux : les services exposent des API REST, GraphQL ou gRPC parce qu'ils ont été construits pour un usage programmatique classique, et la couche IA s'y connecte via des serveurs MCP qui encapsulent ces API et les traduisent en outils MCP — un serveur MCP pour GitHub, par exemple, gère l'authentification et traduit les appels d'outils MCP en appels à l'API REST de GitHub, sans que l'agent ait besoin de connaître cette API directement. Ce découpage en couches — API au niveau des services, MCP au niveau de l'intégration IA — est présenté comme le schéma d'architecture standard émergent.

### Partie 5 — Sécurité, exploitation et effort d'implémentation
Côté sécurité, les API s'appuient sur des mécanismes matures et bien compris (clés API, OAuth 2.0, JWT, limitation de débit, listes blanches d'IP, signature de requêtes). MCP hérite des risques propres aux systèmes d'IA et en ajoute de nouveaux : parce que c'est le modèle qui décide dynamiquement quels outils appeler, la surface d'attaque inclut l'injection de prompt, où du contenu malveillant récupéré par l'agent tente de le détourner vers des appels d'outils non désirés. Les serveurs MCP doivent valider rigoureusement toutes les entrées, les hosts doivent mettre en place des listes blanches d'outils, et le principe du moindre privilège doit s'appliquer strictement : un agent ne devrait être connecté qu'aux serveurs MCP dont il a réellement besoin. Les outils capables d'actions sensibles (suppression de fichiers, envoi d'emails, achats) doivent être assortis de mécanismes de confirmation plutôt que d'être appelables sans aucun contrôle humain.

Côté exploitation, la gestion des API à grande échelle (limitation de débit, cache, répartition de charge, supervision, versionnement) est un problème largement résolu, avec des services de passerelle API managés chez tous les grands fournisseurs cloud. L'outillage opérationnel autour de MCP est plus récent et moins mature : la fiabilité des serveurs, la supervision, la gestion des échecs de connexion et du cycle de vie des sessions avec état restent des sujets sur lesquels les équipes doivent encore investir et établir leurs propres bonnes pratiques.

Côté implémentation, construire un client REST reste une tâche courante et bien outillée dans tous les langages. Construire un serveur MCP demande d'implémenter le protocole (des SDKs existent en Python, TypeScript et d'autres langages) avec un effort comparable à celui d'une API REST, en ajoutant toutefois l'exigence de rédiger des descriptions d'outils suffisamment claires pour qu'un modèle les interprète correctement — une description ambiguë pour un humain le sera tout autant pour un modèle.

### Conclusion de l'article
MCP ne rend pas les API obsolètes, de même que les API n'ont jamais rendu obsolètes les connexions directes aux bases de données : il ajoute une couche qui répond à un problème que les API n'étaient pas conçues pour résoudre, à savoir permettre à des modèles d'IA de découvrir, comprendre et utiliser des capacités externes de façon autonome, sans médiation humaine systématique. Savoir où placer cette couche dans une architecture est, selon l'auteur, ce qui distingue les ingénieurs qui conçoivent des systèmes d'IA réellement efficaces de ceux qui se contentent de recycler des schémas existants sur des problèmes qu'ils ne résolvent pas vraiment.

## Pourquoi ça compte
Cet article offre un cadre de décision clair — API pour le code statique écrit par des humains, MCP pour les agents IA autonomes à l'exécution — particulièrement utile en veille tech alors que l'écosystème des serveurs MCP explose et que de nombreuses équipes doivent choisir comment exposer leurs services à des agents IA sans dupliquer inutilement leurs intégrations existantes.
