## Résumé
Sourcegraph lance Agentic Batch Changes, un agent capable d'appliquer des modifications de code cohérentes sur des centaines, voire des milliers, de dépôts à la fois, à partir d'une instruction en langage naturel. L'outil s'appuie sur Batch Changes (le moteur historique de Sourcegraph pour les changements coordonnés) et sur Deep Search (son agent de compréhension de code), et sait choisir entre écrire un script ou déléguer une tâche à Claude Code ou Codex selon que le changement nécessite du jugement ou non. Des clients comme Mercari (correctif de sécurité) et Canva (migration de bibliothèque) l'ont déjà utilisé pendant la bêta pour fusionner près d'un millier de changesets. Sourcegraph introduit à cette occasion une tarification à la performance : le client ne paie que pour les changesets effectivement fusionnés, pas pour les tokens, les sièges ou les tentatives.

## Points clés
- L'outil s'attaque au problème des changements « transverses » (upgrade .NET, API dépréciée, configuration CI désynchronisée) qui sont faciles à faire dans un seul dépôt mais impossibles à généraliser de façon fiable sur un parc hétérogène.
- Il combine planification, exécution adaptative (le comportement s'ajuste dépôt par dépôt) et réaction automatique aux échecs de CI, jusqu'à ce que les pull requests soient prêtes à être relues par un humain.
- Pour chaque étape, l'agent arbitre entre écrire un script réutilisable (cas majoritaire pour les migrations répétitives) ou confier la tâche à un agent de codage (Claude Code, Codex) quand un jugement contextuel est nécessaire ; l'humain garde la main pour intervenir ou trancher.
- Cas d'usage concrets pendant la bêta : chez Mercari, correction d'une vulnérabilité d'injection de variables d'environnement dans GitHub Actions sur une centaine de dépôts au comportement variable ; chez Canva, migration de bibliothèque via plus de 50 pull requests suivies depuis une seule interface.
- Le modèle de tarification devient « outcome-based » : facturation au changeset réellement fusionné, et non à la consommation de calcul, ce qui aligne le coût sur la valeur livrée.
- Disponible dès aujourd'hui pour les clients de Sourcegraph Cloud, activé par défaut.

## Analyse approfondie
L'article part d'un constat familier à toute grande organisation d'ingénierie : il existe toujours une « liste » de changements transverses en attente — une mise à niveau de framework à propager sur des milliers de dépôts, une API dépréciée encore appelée par une douzaine de services, une configuration d'intégration continue standardisée un jour puis progressivement divergente. Chacun de ces changements est trivial pris isolément, mais à l'échelle du parc complet, les dépôts ne sont jamais parfaitement identiques : ce qui fonctionne à un endroit casse ailleurs, et il n'existe pas de moyen économique de dérouler la modification de façon exhaustive. La liste s'allonge, et plus le changement est important, moins quiconque peut garantir qu'il a bien été appliqué partout où il le fallait : une migration se transforme en centaines de pull requests, sans certitude que le travail est réellement terminé.

Sourcegraph travaille sur ce problème depuis plusieurs années via Batch Changes, son moteur de changement coordonné à travers une base de code, déjà utilisé par certaines des plus grandes organisations d'ingénierie au monde. Le principe : on programme le changement, l'outil ouvre des pull requests partout où il s'applique, puis suit leur progression jusqu'à la fusion. Les clients ont ainsi fusionné des centaines de milliers de changesets, représentant des dizaines de millions de lignes de code ; le plus gros changement unique observé par Sourcegraph a dépassé 2 200 changesets fusionnés.

Le contexte a changé, et la pression ne fait que s'accentuer : les agents de codage produisent du code plus vite qu'aucune équipe ne peut le relire. Plus personne n'a la base de code entière en tête, si bien que chaque modification devient un pari. Les mêmes agents qui simplifient la modification d'un dépôt isolé rendent, paradoxalement, la base de code globale plus difficile à maintenir — et la fameuse liste continue de s'allonger.

Agentic Batch Changes est disponible dès aujourd'hui, construit sur la technologie conçue pour les plus grandes bases de code du monde. Il repose sur deux briques : Batch Changes, pour l'exécution coordonnée, et Deep Search, l'agent de Sourcegraph dédié à la compréhension de bases de code complexes. Ensemble, elles forment un harnais d'agents spécialisé dans l'application de changements à toute échelle, de quelques milliers de dépôts jusqu'aux plus gros monorepos.

Le fonctionnement se veut simple à décrire : on indique en langage naturel ce qui doit changer. L'agent délimite le périmètre du travail à partir de l'index de la base de code, construit un plan, teste le changement sur un premier dépôt, puis le déploie plus largement. Là où les dépôts diffèrent, il s'adapte. Comme un diff ne vaut pas un changement livré, l'agent réagit également si l'intégration continue échoue. Il continue de travailler jusqu'à ce que les pull requests soient prêtes pour une relecture humaine, et suit le statut de fusion de bout en bout, offrant une vue unifiée sur l'avancement du changement. En somme, tout ce qu'un agent de codage isolé peut faire sur un dépôt, Agentic Batch Changes peut l'orchestrer simultanément sur l'ensemble des dépôts d'une organisation.

Pour chaque élément du plan, l'agent détermine s'il nécessite du jugement ou simplement de l'exécution. Quand un jugement est requis, il confie le dépôt concerné à Claude Code ou à Codex, avec des instructions précises et le contexte de la base de code. Le plus souvent, cependant, il préfère écrire un script : une migration de grande ampleur consiste la plupart du temps à répéter le même changement, et exécuter un script est bien plus efficace que de reformuler la même décision des centaines de fois. L'utilisateur voit les diffs se générer au fur et à mesure, peut intervenir à tout moment, et l'agent s'arrête pour poser une question lorsqu'une décision humaine est nécessaire.

Pendant la période de bêta, les clients ont fusionné près d'un millier de changesets créés par Agentic Batch Changes, sur des travaux allant de la remédiation de sécurité aux migrations de bibliothèques.

Chez Mercari, la place de marché japonaise, l'outil a servi à un correctif de sécurité déployé sur de nombreux dépôts. Patrick Klitzke, chef d'équipe chez Mercari, l'a utilisé pour repérer une vulnérabilité d'injection par variables d'environnement dans GitHub Actions à travers la base de code de l'entreprise, puis pour appliquer le correctif sur les dépôts concernés. Il témoigne : « J'ai examiné un problème d'injection GitHub lié à un mauvais paramétrage des variables d'environnement. J'ai pu le corriger avec un seul prompt, à la fois sur le frontend et le backend du centre d'aide, puis étendre cela à tous les dépôts de Mercari. J'ai trouvé environ 80 dépôts potentiellement concernés. » Il ajoute : « Avec Agentic Batch Changes, on peut traiter des dépôts aux configurations similaires mais non identiques. Un changement scripté classique se limiterait le plus souvent à une recherche-remplacement textuelle, sans aucun contexte sur la façon dont le code est réellement utilisé. »

Chez Canva, l'usage concernait une migration de bibliothèque. L'alternative aurait été soit quelques pull requests surdimensionnées, soit un tableur pour suivre une multitude de petites PR. À la place, Agentic Batch Changes a ouvert les pull requests et suivi chacune d'elles jusqu'à la fusion depuis une vue unique. William L., ingénieur logiciel senior chez Canva, explique : « Nous avons utilisé Agentic Batch Changes pour ouvrir et fusionner plus de 50 pull requests sur nos dépôts dans le cadre d'une migration de bibliothèque. L'interface web a facilité le suivi de chaque PR et de son statut. Sans cet outil, nous aurions dû gérer soit d'énormes PR, soit des tableurs ; Agentic Batch Changes a simplifié le processus, aussi bien pour les relecteurs que pour moi. »

La remédiation de sécurité et les migrations de bibliothèques ne sont que deux cas d'usage parmi d'autres. Sourcegraph mentionne aussi les montées de version de dépendances, le remplacement d'API dépréciées, le déploiement de nouveaux frameworks, la modernisation des pipelines CI et la gestion des échéances de fin de vie logicielle. Ce ne sont que des points de départ : les clients trouvent continuellement de nouveaux usages que l'entreprise n'avait pas anticipés, et elle dit vouloir en entendre parler.

Avec le lancement d'Agentic Batch Changes, Sourcegraph introduit une tarification fondée sur le résultat : le client paie par changeset effectivement fusionné dans sa base de code, et non par token, par siège ou par tentative. Si une pull request est ouverte mais que l'équipe décide de ne pas la fusionner, elle n'est pas facturée. Ce choix de tarification est présenté comme la manière la plus claire d'afficher la confiance de Sourcegraph dans la qualité du travail produit, et comme un moyen pour les clients de justifier la dépense par rapport à quelque chose de concret — un changement réellement livré plutôt qu'une prévision de consommation de calcul.

Agentic Batch Changes est disponible dès aujourd'hui pour les clients de Sourcegraph Cloud, activé par défaut. L'entreprise invite les intéressés à contacter leur équipe de compte ou à demander une démonstration, avec plus d'informations sur sourcegraph.com/agentic-batch-changes.

## Pourquoi ça compte
Ce lancement illustre une tendance de fond en ingénierie logicielle assistée par IA : le passage de l'agent de codage « par dépôt » à l'orchestration d'agents à l'échelle de tout un parc, avec une tarification calée sur le résultat plutôt que sur la consommation de calcul — un signal à suivre pour quiconque anticipe l'évolution des offres DevTools/AgentOps et des modèles de pricing associés.
