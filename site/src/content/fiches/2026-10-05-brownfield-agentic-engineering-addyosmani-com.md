## Résumé
Addy Osmani explique comment utiliser des agents IA de codage dans des bases de code anciennes (« brownfield »), où le dépôt ne décrit plus fidèlement le comportement réel du système et où de nombreuses contraintes vivent hors du code (connaissances tribales, dépendances d'autres équipes, historique). Sa thèse centrale : l'autonomie donnée à un agent doit dépendre du rayon d'impact (« blast radius »), de l'observabilité et de la capacité à revenir en arrière — pas de la confiance affichée par le modèle. Il propose un cadre opérationnel (zones vert/jaune/rouge, mémos de recherche durables, tests de caractérisation avant toute modification, migrations complètes plutôt que partielles) illustré par des cas réels (Netflix, Bun, Stripe, Shopify, Asana, Spotify, Google). Conclusion : les agents rendent les réécritures moins chères à essayer, mais ne changent pas le niveau de preuve nécessaire pour valider un changement.

## Points clés
- Classer le code en zones vert (tests solides, isolé → boucle rapide d'agent), jaune (qualité mixte → tests de caractérisation avant modification) et rouge (auth, facturation, paie → supervision humaine systématique) ; c'est toujours un humain qui dessine la carte, jamais l'agent.
- Ne documenter pour l'agent que ce que le code ne peut pas dire lui-même (conventions non écrites, arbitrages historiques, contraintes externes) — l'agent infère déjà très bien le reste depuis le code.
- Produire des artefacts de recherche durables (mémo de compréhension avec sources citées) pour que chaque session n'ait pas à refaire la même archéologie du code.
- Transformer toute correction répétée en mécanisme automatisé (lint, hook, type, test) plutôt que de la corriger silencieusement à chaque fois.
- Verrouiller le comportement actuel avec des tests de caractérisation écrits par un humain (ou dans une passe séparée) avant de laisser un agent refactorer, et toujours migrer en unités complètes (ancien chemin supprimé), jamais à moitié.
- Paralléliser seulement après avoir validé un « juge » automatisé fiable sur une unité ; sinon la parallélisation ne fait qu'amplifier le goulot d'étranglement de la revue humaine.

## Analyse approfondie

**Le problème brownfield.** Une base de code ancienne n'est plus une description complète de son propre comportement : savoir tacite, rustines, services legacy et attentes d'autres équipes vivent hors du dépôt. Lancer des agents sans supervision sur un tel système produit souvent un code qui « fonctionne » mais avec une architecture erronée et des tests fragiles. Pour l'auteur, le code doit rester la source de vérité ; tout ce qu'on ajoute en complément doit couvrir uniquement ce qui ne peut pas être inféré du code lui-même.

**Les zones.** L'auteur propose de cartographier le dépôt en trois zones. La zone verte regroupe le code bien testé, isolé, utilisant des conventions modernes : les agents peuvent y travailler en boucle rapide et autonome. La zone jaune, de qualité mixte, nécessite l'écriture de tests de caractérisation avant toute modification par un agent. La zone rouge couvre les parties sensibles — authentification, facturation, permissions, paie — où les réécritures non supervisées sont proscrites, notamment quand seule une poignée de personnes comprend vraiment le fonctionnement du système. Trois règles rendent ce découpage opérationnel plutôt que symbolique : (1) c'est un humain, jamais l'agent, qui trace la carte — laissé seul, un agent commence par le fichier le plus intimidant car ses noms semblent les plus intéressants ; (2) une zone ne change de couleur que lorsque c'est mérité, par exemple le jaune devient vert une fois les tests de caractérisation écrits et le propriétaire du module ayant relu les premières modifications de l'agent ; (3) chaque zone définit le mode opératoire : boucle libre en vert, tests d'abord en jaune, binôme humain à chaque étape en rouge (ou pas de travail du tout).

**Écrire ce que le code ne peut pas dire.** L'autonomie devrait suivre le rayon d'impact, l'observabilité et la réversibilité — pas la confiance affichée par le modèle. Les agents infèrent très bien la structure du système à partir du code ; il est inutile de leur fournir des fichiers markdown exhaustifs qui saturent la fenêtre de contexte. Ce qui compte réellement : les nuances propres à l'équipe ou au métier, les arbitrages expliquant pourquoi le système est structuré ainsi, les règles non imposées par l'outillage statique, les contraintes externes et l'historique derrière des implémentations à première vue contre-intuitives. En somme : écrire ce que le code ne peut pas dire, et rien de plus.

**Faire survivre la recherche à la session.** Si l'exploration d'un agent ne produit aucun artefact durable, l'agent suivant repaie le même travail d'archéologie. Pour les zones jaune et rouge, l'auteur recommande une passe de lecture séparée produisant un mémo de compréhension court : points d'entrée, propriétaires, appelants, abstractions existantes, tests, signaux de production, historique pertinent et questions ouvertes — chaque affirmation devant citer un fichier, un ticket, un enregistrement de propriété ou un tableau de bord. Sans cela, la boucle par défaut gaspille sa propre recherche : l'agent comprend le fonctionnement du flux d'authentification, termine la tâche, puis perd ce modèle mental à la fin de la session (l'historique de chat n'étant pas un bon système d'enregistrement, surtout après compaction). Ensuite, la planification devrait repartir d'un contexte propre : quels fichiers les approches envisagées touchent-elles, quels invariants préservent-elles, comment les annuler ? Un humain choisit la voie. L'implémentation doit s'arrêter si elle découvre que la carte était fausse. La revue repart elle aussi de zéro et travaille à rebours depuis les critères d'acceptation — un relecteur « frais » remarque mieux qu'un test valide l'implémentation sans couvrir l'exigence réelle.

**Quand les instructions deviennent un harnais.** Chaque correction répétée révèle une pièce manquante du harnais de travail. Les instructions consignent les faits inhabituels d'un dépôt ; les skills packagent des procédures réutilisables (vérifier le rayon d'impact, valider un changement de schéma) ; les plugins donnent un accès gouverné au catalogue de propriété, aux archives d'incidents ou aux tableaux de bord. Le harnais, c'est l'environnement de travail autour de l'agent : contexte, outils, permissions, tests, logs, récupération. Une « factory » planifie de nombreuses boucles fiables, conserve un état durable, et renvoie les cas nouveaux à des humains. Le test pratique : que se passe-t-il quand l'agent se trompe ? Si on corrige silencieusement le diff, la session suivante répétera l'erreur. Quand le même commentaire de revue réapparaît, il faut le transformer en règle de lint, hook, type, test ou skill — garder du texte libre seulement pour ce qui ne peut pas être imposé mécaniquement. Une règle de refus, un identifiant à portée limitée ou un contrôle CI n'ont pas besoin de « se souvenir » : avec le temps, le harnais devient la trace des erreurs que l'équipe a décidé de ne plus payer deux fois.

**Commencer par du travail à risque nul.** Il s'agit de verrouiller le comportement actuel avant de laisser quoi que ce soit l'améliorer. Plutôt que de réécrire un monolithe en Rust d'emblée, on commence par expliquer comment les choses fonctionnent, puis on génère des tests de caractérisation qui documentent le comportement réel actuel — y compris ses aspects disgracieux, car dans un vieux système ce comportement imparfait est parfois ce sur quoi l'activité repose, et un agent « corrigera » volontiers ce défaut sous couvert d'une suite verte. Netflix a appliqué la même logique à l'échelle de la production lors de sa migration GraphQL : rejouer et dupliquer (« shadow ») le trafic sur l'ancien et le nouveau chemin, comparer les réponses (« diff »), ne promouvoir qu'en cas de correspondance — c'est la voie à suivre quand une surface critique (type page d'accueil) n'a pas de suite de tests unitaires fiable : ne pas deviner, faire tourner les deux et comparer. Si c'est l'agent lui-même qui fait passer ces tests, il ne faut pas que cette même session en soit le seul auteur : fixer le comportement d'abord, dans une passe séparée ou par un humain, puis laisser l'agent travailler — sinon on obtient une suite verte qui encode l'implémentation qu'on vient d'inventer. Ensuite viennent les transformations mécaniques (inventaire du code mort, des exports inutilisés), en évitant de commencer par les parties les plus complexes du système. L'auteur illustre ce principe de prudence par une anecdote personnelle chez AOL : rappelé un jour de congé parce que la page d'accueil d'AOL.com était cassée et que personne d'autre ne maîtrisait assez JavaScript, il a dû, en l'absence de couverture de tests pour de nombreux composants gérés par des dizaines de départements différents, recourir à des tests utilisateurs manuels pour vérifier que rien n'était cassé ailleurs. Cette réalité n'a pas changé : les agents ne suppriment pas le problème des « dizaines de départements », ils rendent seulement moins coûteuse la tentative de changement face à ce problème. Une surface que seul le trafic de production comprend vraiment reste par définition une zone rouge, et tant qu'on n'a pas construit un substitut à ce trafic, le test utilisateur manuel reste le garde-fou.

**Migrer en unités complètes.** Une migration n'est terminée que lorsque le nouveau chemin fonctionne et que l'ancienne dépendance a démontrablement disparu. Les migrations à moitié faites perturbent particulièrement les agents : une recherche renvoie l'ancienne approche dans quarante fichiers, le remplacement dans douze, et une couche de compatibilité qui présente les deux comme actuels — l'agent se retrouve devant des précédents contradictoires. L'auteur préfère finir une seule voie de bout en bout, suppression de l'ancien chemin incluse, plutôt que de convertir trente fichiers en laissant les deux motifs coexister ; si la suppression est reportée à un futur ticket de nettoyage, l'unité de migration n'est pas complète. Les tests peuvent rester verts alors même qu'un remplacement appelle encore l'implémentation historique — le benchmark SWE Refactor Bench appelle ce phénomène la « Blindness » (« cécité ») : sur 520 exécutions d'agents, seules 28 ont passé son audit de migration, les tests comportementaux et une vérification indépendante. Quand un codemod peut effectuer le changement de façon routinière, mieux vaut utiliser l'agent pour aider à l'écrire et le vérifier, et lui confier la file des exceptions. La migration TypeScript de Stripe est un exemple pertinent précisément parce qu'aucun agent n'y a participé : l'artefact durable, c'était la machine de migration elle-même.

**Les leçons des grandes migrations.** Le portage Zig vers Rust de Bun a fait tourner environ 50 workflows sur 11 jours pour une base de 535 000 lignes, avec deux relecteurs adversariaux sur chaque unité générée et toute la suite de tests préexistante comme condition de fusion ; l'élément à reproduire est que des heures ont été investies dans un guide de portage faisant correspondre les idiomes Zig et Rust avant même de lancer un agent. Le propre processus de migration d'Anthropic teste son propre « livre de règles » sur une mini-migration jetable et jette le résultat de cet essai avant de lancer la migration à grande échelle. Une étude contrôlée de migration VB6 vers C# a mesuré une équivalence comportementale de 92 % sur les fonctionnalités simples contre 47 % sur les complexes : la taille de l'unité est le levier déterminant. Ce schéma précède d'ailleurs largement les agents : Stripe a déplacé 3,7 millions de lignes vers TypeScript en une seule pull request grâce à des mois de travail de codemod, sans aucun agent impliqué, et le chapitre de Google sur les « large-scale changes » explique pourquoi les changements atomiques se réduisent à mesure que les bases de code grossissent. Spotify annonce désormais plus de 650 pull requests générées par agents fusionnées chaque mois, sur des rails construits des années plus tôt par Backstage. Asana a résorbé en deux semaines calendaires un arriéré pluriannuel lié à Enzyme, pour environ 12 000 dollars de coût de modèle et d'infrastructure — une somme qui ne représente qu'une facture de tokens, pas un substitut à l'estimation de staffing sur cinq ans qu'ils avaient sur les livres ; il faut la traiter comme un coût de génération rapporté par le fournisseur, pas comme une étude contrôlée d'économies. Ce qui est transférable, comme pour Bun : une migration mécanique bien délimitée, une suite préexistante, et des humains qui continuent de relire chaque changement. Ce qui se transfère réellement d'une entreprise à l'autre, c'est la structure organisationnelle autour des agents, pas les agents eux-mêmes.

**Ce qui a vraiment changé.** Les agents ont modifié le prix d'essayer plusieurs implémentations plausibles ; ils n'ont pas changé le niveau de preuve nécessaire pour en choisir une. Des directions techniques autorisent désormais leurs équipes à faire tenter plusieurs réécritures dans des langages ou frameworks différents, car cela devient moins coûteux de comparer les compromis. Shopify a reconstruit son application grand public Shop, de React Native vers Swift et Kotlin natifs, en douze semaines avec une petite équipe, via des points de contrôle « taille d'écran » validés par agent. L'application marchande, bien plus grande, reste le problème brownfield classique : des centaines d'écrans, une intégration plateforme profonde, les mêmes garde-fous, mais un calendrier plus long. On peut désormais faire implémenter la même fonctionnalité par plusieurs options concurrentes plutôt que de choisir une seule équipe et un seul pari : toutes passent les mêmes tests unitaires, on peut profiler leurs performances, puis trancher — une démarche bien moins coûteuse qu'auparavant.

**Paralléliser en dernier.** Plus de code généré devrait entraîner une revue humaine plus sélective, pas moins de responsabilité humaine. Les « software factories » peuvent lancer de nombreux changements en parallèle, mais l'auteur ne recommande de reproduire cela qu'une fois qu'une seule unité dispose d'un juge fiable, d'un chemin de récupération et d'un format de revue que les humains peuvent absorber. La parallélisation multiplie le goulot d'étranglement existant : une vérification automatisée peut gérer cinq changements contrôlés, alors qu'un senior relisant chaque ligne se retrouve avec une file d'attente, une attention fragmentée et, à terme, une approbation de pure forme. L'auteur préfère une revue automatisée qui ouvre sur l'intention, les invariants modifiés, les résultats de tests, les écarts de parité et la voie de retour en arrière, le diff complet restant disponible ; l'attention humaine doit se porter d'abord sur le rayon d'impact le plus large et l'oracle le plus faible. Les worktrees isolent les changements, pas le comportement : ils peuvent partager les métadonnées Git, les identifiants, les services locaux et l'accès réseau — un compromis acceptable pour du travail de confiance, mais des agents non supervisés consommant du contenu non fiable nécessitent des sandboxes plus robustes et des identifiants à portée limitée.

**Les agents mettent un prix sur l'ambiguïté.** Le nombre de lignes générées ne dit rien sur l'amélioration réelle du code. L'auteur préconise de suivre plutôt le délai de livraison, le temps de revue, les interventions humaines, les défauts échappés, les retours en arrière, les écarts d'oracle et les suppressions laissées de côté. Pour une migration spécifiquement : les imports historiques restants, le trafic servi par le nouveau chemin, les écarts de parité et les dépendances legacy supprimées — une suite verte alors que tout le trafic passe encore par l'ancien chemin n'est que de l'agitation sans effet. Les agents rendent visible un coût qui existait déjà, payé lors de l'intégration, de la revue et de la récupération d'incident ; les conventions tribales deviennent des commentaires de revue récurrents. Cela constitue en réalité un argument renforcé en faveur du travail de maintenance que les équipes savaient déjà précieux. La prochaine fois qu'un agent travaillera sur l'équivalent d'une page d'accueil critique, l'auteur souhaite qu'il laisse derrière lui plus qu'une simple réparation : un parcours utilisateur synthétique, un enregistrement de propriété et un test de régression — ce qui compte aussi, c'est ce qu'hérite le prochain ingénieur, humain ou agent.

## Pourquoi ça compte
Ce texte offre un cadre concret et testé sur le terrain pour encadrer l'usage d'agents IA sur des bases de code existantes — un sujet central pour toute organisation qui expérimente l'ingénierie agentique au-delà des projets neufs. Il fournit aussi un vocabulaire opérationnel (zones, rayon d'impact, tests de caractérisation, unités de migration complètes) directement réutilisable pour structurer une politique interne d'adoption des agents de codage.
