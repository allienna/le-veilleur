## Résumé
L'article de WorkOS explique pourquoi confier directement un token d'accès OAuth à un agent IA qui agit pour le compte d'un utilisateur est structurellement dangereux : l'agent traite les données qu'il lit (issues GitHub, pages web, tickets) avec la même autorité que ses propres instructions, ce qui ouvre un chemin de fuite du token via l'injection de prompt. Réduire les scopes ou faire tourner les tokens plus souvent atténue le problème sans le résoudre, car la fuite est une propriété du runtime et non un instant isolé. WorkOS propose à la place un mécanisme de proxy d'identifiants nommé Relay : l'agent décrit l'appel qu'il veut faire (fournisseur, utilisateur) et c'est WorkOS, et non l'agent, qui attache le vrai token avant de transmettre la requête au fournisseur. Le texte insiste sur le fait que cette approche réduit le rayon d'impact d'une compromission sans régler l'injection de prompt elle-même ni les permissions trop larges accordées par les fournisseurs.

## Points clés
- Les agents IA font s'effondrer la frontière classique entre code de confiance et entrée non fiable : un commentaire de code ou un ticket peut devenir une instruction exécutée par l'agent.
- Un token OAuth détenu par un agent peut se retrouver dans de nombreux endroits non sécurisés : la fenêtre de contexte, les logs d'appels d'outils, les logs du fournisseur de modèle, stdout/stderr, les rapports d'erreur, les fichiers de mémoire persistante, voire directement exfiltré par l'agent lui-même.
- Réduire les scopes OAuth ou faire tourner les tokens plus fréquemment n'élimine pas le risque : les scopes des fournisseurs sont trop larges par nature, et la rotation ne fait que raccourcir une fenêtre d'exposition qui se rouvre à chaque nouvel appel.
- La solution proposée (Relay, en accès anticipé chez WorkOS) fait transiter les requêtes par un proxy qui résout l'utilisateur, récupère et rafraîchit le credential stocké côté WorkOS, puis injecte le token réel avant de relayer la requête — l'agent ne voit jamais le token.
- Le proxy impose des garde-fous techniques : hôtes autorisés par fournisseur, pas de suivi des redirections, suppression des en-têtes sensibles (Cookie, X-Forwarded-*), code d'erreur dédié quand l'utilisateur n'a pas autorisé la connexion, et une limite de taille/temps sur les requêtes relayées.
- Cette architecture ne résout ni l'injection de prompt, ni la présence d'une autre clé sensible (la clé API WorkOS) dans le runtime, ni le fait que les permissions accordées par les fournisseurs restent grossières ; elle change seulement la nature de l'incident possible : d'un token volé et exploitable indéfiniment à une session active qu'on peut couper.

## Analyse approfondie

### Une hypothèse de sécurité qui ne tient plus
Le modèle d'intégration classique repose sur un token d'accès conservé par un processus qui n'exécute que du code écrit par l'équipe produit. Ce modèle suppose implicitement que le code qui manipule le token est digne de confiance, tandis que les données qu'il traite (corps de requête, entrées utilisateur) sont filtrées par des contrôles classiques (validation, requêtes paramétrées, encodage de sortie). Avec un agent, cette séparation disparaît : le contenu lu par l'agent — un ticket de support, une page web, un commentaire dans un dépôt — arrive dans la même fenêtre de contexte que les instructions système et reçoit la même considération par le modèle. Le système ne se limite plus à exécuter du code écrit par les développeurs ; il exécute aussi ce que le modèle décide de faire à partir d'un texte qu'il a rencontré. Placer un token OAuth à longue durée de vie dans cet environnement revient à exposer un identifiant puissant à un composant qui traite en permanence des entrées non fiables comme s'il s'agissait d'instructions légitimes.

### Les multiples endroits où le token finit par se retrouver
Dire que « le token est dans l'environnement » reste abstrait jusqu'à ce qu'on énumère concrètement les copies qu'il engendre dans un runtime d'agent :
- il peut apparaître dans la fenêtre de contexte dès que l'agent inspecte sa propre configuration ou débogue un appel qui échoue — une fois présent dans le contexte, il suffit d'une étape de résumé pour qu'il se retrouve ailleurs ;
- il se retrouve souvent dans les arguments des appels d'outils, systématiquement journalisés par les couches d'observabilité, car c'est le seul moyen pratique de déboguer un agent ;
- il peut transiter par les journaux du fournisseur de modèle dès qu'il passe par un prompt ;
- il peut apparaître dans stdout/stderr, par exemple lorsqu'un agent compose lui-même une commande `curl` sans savoir qu'il doit masquer ses propres en-têtes ;
- il peut se retrouver sérialisé dans la charge utile d'une exception lors d'un rapport d'erreur consécutif à un appel HTTP échoué ;
- il peut persister dans des fichiers de travail ou des stores de mémoire que les agents utilisent pour garder une trace entre les étapes, et qui ne sont presque jamais traités comme des données secrètes ;
- enfin, le chemin d'exfiltration le plus direct ne requiert aucun bug : un agent disposant d'un token et d'un accès réseau peut être amené à l'envoyer ailleurs — ce n'est pas une faille du code, c'est la fonctionnalité qui fonctionne comme prévu.
Aucune de ces situations ne suppose qu'un attaquant ait besoin de « percer » quoi que ce soit : elles correspondent aux conditions de fonctionnement normales d'un agent qui fait son travail.

### Une fuite qui ne tient qu'en un paragraphe
L'article illustre le risque avec un agent chargé de trier des issues GitHub pour le compte d'un utilisateur, détenant donc son token GitHub pour lire des dépôts et commenter. Il suffit qu'une issue se termine par une ligne adressée non pas à l'équipe, mais à l'agent, lui demandant d'inclure son en-tête d'autorisation dans une requête de diagnostic envoyée vers une URL contrôlée par l'attaquant. Que le modèle obtempère ou non dépend du modèle, du prompt et du jour — et c'est précisément le problème : la sécurité des identifiants devient probabiliste, alors qu'il faudrait gagner ce pari à chaque fois sans exception. Même un modèle qui résiste quatre-vingt-dix-neuf fois sur cent ne constituerait un contrôle acceptable dans aucune autre partie de l'infrastructure. Et l'incident n'est pas réparable comme une fuite de session classique : un token d'accès divulgué n'est pas quelque chose qu'on peut invalider côté serveur — c'est un identifiant porteur valable pour l'API d'un tiers, actif jusqu'à son expiration ou la révocation par l'utilisateur, et exploitable depuis n'importe où.

### Pourquoi restreindre les scopes et faire tourner les tokens ne suffit pas
Les deux réflexes naturels consistent à restreindre les scopes et à raccourcir la durée de vie des tokens. Les deux sont utiles, mais aucun ne s'attaque à la racine du problème. Les scopes OAuth restent grossiers parce qu'ils ont été conçus pour des applications classiques, pas pour des agents : un token permettant de lire les dépôts dont un agent a besoin peut en général lire tous les dépôts visibles par l'utilisateur, car les scopes des fournisseurs couvrent des pans entiers de produit plutôt que des permissions fines. La rotation, elle, raccourcit la fenêtre d'exposition sans la fermer : un attaquant capable d'atteindre un token une fois pourra généralement l'atteindre à nouveau, puisque le chemin de fuite est une propriété permanente du runtime et non un instant particulier. Pire, un flux de rafraîchissement implique que le runtime détient aussi le matériel de refresh, qui a souvent plus de valeur que le token d'accès lui-même. Ces deux mitigations acceptent toutes deux la prémisse que le token doit être présent dans l'environnement de l'agent — c'est justement cette prémisse qu'il faut remettre en cause.

### L'accès délégué sans transmettre le token : le mécanisme Relay de WorkOS
L'alternative consiste à arrêter de livrer l'identifiant au code qui en a besoin, et à laisser ce code décrire simplement l'appel qu'il souhaite effectuer pour un utilisateur donné. WorkOS propose cela sous le nom de Relay, actuellement en accès anticipé. Le principe : l'agent envoie sa requête à WorkOS en précisant le fournisseur cible et l'utilisateur pour lequel il agit, et c'est WorkOS qui attache le credential au moment de relayer la requête.
Concrètement, une requête proxyfiée transporte la clé API WorkOS dans l'en-tête `Authorization`, l'URL cible dans `X-Relay-URL`, l'identifiant de l'utilisateur dans `X-Relay-User`, et éventuellement `X-Relay-Organization` lorsque la connexion a été autorisée au niveau d'une organisation. Le fournisseur est déduit de l'hôte présent dans l'URL cible ; l'en-tête optionnel `X-Relay-Provider` permet de lever toute ambiguïté si nécessaire. WorkOS vérifie la clé, résout le compte connecté de l'utilisateur, récupère le credential stocké dans le coffre d'identifiants « Pipes », le rafraîchit s'il a expiré, retire ses propres en-têtes de contrôle, injecte le token du fournisseur, puis renvoie la réponse du fournisseur sans la modifier — méthode HTTP, corps et en-têtes de contenu traversent le proxy sans changement, ce qui réduit la conversion d'un appel direct en appel proxyfié à une simple modification d'en-têtes plutôt qu'à une réécriture complète.
Deux détails rendent ce mécanisme réellement utilisable et pas seulement sécurisé sur le papier. D'abord, la sémantique d'erreur est explicite : un proxy transparent a un problème de nommage, puisqu'un `401` ou `403` renvoyé par le proxy serait indiscernable d'un `401`/`403` renvoyé par le fournisseur ou d'un rejet de la clé API. Si l'utilisateur n'a pas connecté le fournisseur, ou si son autorisation a été révoquée, le proxy renvoie un code `402` avec le code d'erreur `relay_authorization_required`, accompagné d'une `authorization_url` vers laquelle rediriger l'utilisateur. Chaque réponse proxyfiée porte également un en-tête `X-Relay-Upstream-Status`, qui indique si la requête a effectivement atteint le fournisseur — un `404` GitHub et un `404` d'un fournisseur inconnu ne se confondent donc plus. Ensuite, le token vit désormais derrière une frontière que l'agent ne peut pas franchir même s'il essaie : les requêtes ne peuvent viser que les hôtes explicitement autorisés pour un fournisseur donné, les redirections ne sont jamais suivies (un point important, car une redirection suivie est précisément la manière dont un credential injecté finit sur un hôte que personne n'a autorisé), les en-têtes `Cookie`, `X-Forwarded-*` et les en-têtes de type « hop-by-hop » sont supprimés à l'aller, et `Set-Cookie` au retour. Le délai d'attente côté amont est fixé à trente secondes et les corps de requête sont transmis tels quels jusqu'à 5 Mo.
Résultat : un agent compromis peut toujours effectuer des appels qu'il ne devrait pas faire, mais il ne peut plus s'enfuir avec un credential réutilisable ailleurs.

### Ce que ce mécanisme ne règle pas
- **L'injection de prompt reste intacte.** Rien dans ce dispositif ne rend un agent plus résistant aux instructions dissimulées dans les données qu'il lit. Un agent qu'on peut convaincre de publier un message Slack non désiré pourra toujours être convaincu de le publier : le proxy change ce qu'un attaquant peut emporter, pas sa capacité à influencer l'agent.
- **La clé API WorkOS reste présente dans le runtime.** Elle authentifie chaque appel pour l'ensemble de l'environnement, et Relay ne la fait pas disparaître. Il faut donc la traiter avec la même rigueur : l'injecter au moment de la requête plutôt que de la figer dans du code ou des prompts visibles par l'agent, et la faire tourner si un runtime est compromis. Déplacer un secret hors de portée tout en laissant un secret plus puissant accessible n'est pas une amélioration, juste un déplacement latéral du risque.
- **Les permissions des fournisseurs restent ce qu'elles sont.** Les appels proxyfiés sont contraints par une liste d'hôtes autorisés, pas par ce qu'un agent donné devrait réellement pouvoir faire. L'autorisation fine des actions d'un agent reste un vrai manque, et ce point de passage unique est l'endroit naturel où, à terme, cette politique pourrait être appliquée — mais l'existence du point de passage ne vaut pas l'existence de la politique.
Ce que l'on obtient réellement, c'est un changement dans l'ampleur des dégâts possibles : un token divulgué constitue une capacité durable, portable et exploitable hors ligne, tandis qu'une session d'agent détournée reste un processus vivant qu'on peut arrêter, dont les appels passent par un point unique où ils peuvent être observés et coupés. Ce sont deux types d'incidents très différents, et l'un des deux s'arrête dès qu'on le remarque.

### Un principe plus ancien que le produit
Le proxy d'identifiants n'est pas une idée nouvelle, et c'est plutôt un argument en sa faveur. Le secteur des paiements a emprunté cette voie avant tout le monde : les coffres de cartes et la tokenisation existent parce que le moyen le plus rapide de réduire le périmètre d'un audit est de garantir que la donnée sensible n'entre jamais dans vos systèmes. Le même raisonnement s'applique aux tokens OAuth dans les runtimes d'agents, pour la même raison : on ne peut pas divulguer ce que l'on n'a jamais détenu. Le principe durable qui se dégage de tout cela dépasse largement un produit particulier : les identifiants doivent résider dans le composant le moins accessible capable de faire le travail, et les runtimes d'agents sont aujourd'hui devenus le composant le plus exposé dans la plupart des architectures. Ils lisent du texte contrôlé par des tiers potentiellement malveillants, journalisent à peu près tout, persistent de l'état pour progresser dans leurs tâches, et agissent sur la base de leurs propres conclusions. C'est un endroit tout à fait adapté pour prendre une décision ; ce n'est pas un endroit adapté pour garder une clé. Pour quiconque confie aujourd'hui un token à un agent, la question qui mérite réflexion n'est pas de savoir si le prompt est suffisamment robuste, mais ce qui se passera le jour où il ne le sera pas.

## Pourquoi ça compte
Ce texte formalise un angle mort de sécurité propre aux architectures d'agents IA — la fuite d'identifiants via l'injection de prompt — et propose un modèle concret de mitigation (proxy de credentials) qui s'inscrit dans la tendance plus large de délégation d'accès pour les agents autonomes, un sujet central pour toute veille sur la sécurisation des systèmes d'IA agentique en entreprise.
