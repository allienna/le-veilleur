## Résumé

Netflix a développé un système d'agents IA autonomes pour détecter et corriger les problèmes de performance introduits par du code généré de plus en plus rapidement, notamment via l'assistance IA. L'article explique comment des LLM, alimentés par des données de profiling (flame graphs, traces CPU/mémoire), parviennent à repérer des anti-patterns classiques (complexité quadratique, regex sur le chemin critique, allocations mémoire inutiles, mauvais usage de librairies) et à proposer des correctifs vérifiés via tests, déploiement canari et revue humaine avant fusion. Netflix a aussi mis en place un « Pattern Catalog » (simple dépôt Git de fichiers Markdown) pour partager les découvertes entre équipes et détecter les anti-patterns dès la pull request, avant même la mise en production. L'article conclut sur une grille de maturité en 4 niveaux, de l'analyse manuelle (niveau 0) à l'autonomie complète des agents (niveau 3), Netflix se situant aujourd'hui au niveau 2 (orchestration).

## Points clés

- Le travail traditionnel de performance engineering est lent, manuel et dépend d'un petit nombre d'experts capables de lire des flame graphs — ce qui ne scale pas face au volume de code généré par IA.
- Les LLM n'ont pas de visibilité sur l'environnement d'exécution réel (charge, container, fréquence d'appel), mais ils reconnaissent bien les anti-patterns de performance appris sur de vastes corpus de code (boucles quadratiques, invariants de boucle recalculés, N+1 queries, allocations excessives).
- En production, l'agent de Netflix a trouvé 4 catégories de bugs majeurs : une agrégation en O(N²) sur des streams Java (8,8 % de CPU gaspillé), une regex exécutée à chaque requête (46 % du CPU, corrigée avec un gain ×22), des allocations d'objets redondantes causant des OOM (47 % des collections de heap), et un compteur de métriques relooké à chaque appel (66 % du CPU contre 0,3 % pour la logique métier).
- Toute correction proposée par l'agent passe par un pipeline de vérification strict : tests existants, déploiement canari comparé à une version de référence, rapport de télémétrie (CPU, latence P99, allocations), puis décision finale humaine via pull request — aucune action n'est appliquée automatiquement sans validation.
- Pour éviter de refaire les mêmes découvertes à chaque service, Netflix a créé un « Pattern Catalog » : un dépôt Git de fichiers Markdown, centralisé, réutilisable dans plusieurs contextes (profiling offline, vérifications CI/CD, outils locaux) et facilement injectable dans le prompt système d'un LLM.
- Netflix distingue une approche réactive (profiling continu en production puis correction) et une approche proactive (détection d'anti-patterns connus dès la pull request, avant la mise en production), avec une grille de maturité en 4 niveaux allant du tout-manuel à l'autonomie complète des agents.

## Analyse approfondie

**Les limites du travail de performance traditionnel.** Chez Netflix, l'optimisation de performance reposait sur une boucle itérative largement manuelle : déclencher un profiler sur un serveur de production, récupérer les traces ou flame graphs bruts, les analyser visuellement pour repérer des cadres de pile anormalement larges, remonter dans le code pour comprendre des noms de méthodes souvent cryptiques, identifier l'opération inefficace, écrire un correctif, puis le déployer et mesurer l'effet — avant de recommencer le cycle à chaque nouveau déploiement. Ce processus dépend d'un petit nombre d'experts capables de lire des exécutions bas niveau ; faute de temps, seules les incidents majeurs ou ralentissements évidents sont investigués, les fuites de ressources plus discrètes passant sous le radar.

**Le problème du code généré par IA.** L'essor des assistants de code a aggravé la situation pour deux raisons : un « piège de la vitesse » (du code peut être produit jusqu'à 10 fois plus vite, quel que soit le niveau du développeur, sans garantie de performance) et un « fossé contextuel » (un LLM écrit un code syntaxiquement correct et fonctionnellement testé, mais il ignore tout de l'environnement d'exécution réel : fréquence d'appel sur un chemin critique, pression mémoire dans un container à charge maximale, etc.). Un code qui semble correct en isolation peut donc gaspiller énormément de ressources à l'échelle.

**Les LLM face aux données de profiling.** Netflix a testé si un LLM pouvait directement interpréter des données de profiling brutes. Bien que chaque langage ait son propre profiler (async-profiler ou Java Flight Recorder pour la JVM à 100 Hz, py-spy pour Python, pprof pour Go), tous décomposent l'exécution en piles d'appels et mesurent deux métriques communes : le temps inclusif (temps total passé dans une fonction et ses appels enfants) et le temps propre/CPU (temps passé uniquement dans le code de la fonction elle-même). Cette similarité structurelle permet à un seul pipeline analytique de traiter des données issues de presque n'importe quel runtime. De plus, les LLM, entraînés sur d'immenses bases de code, reconnaissent nativement des anti-patterns classiques : boucles quadratiques, invariants de boucle recalculés à chaque itération, allocations d'objets excessives sur le chemin critique, requêtes « N+1 ». Il ne s'agit donc pas de demander au modèle de deviner la cause d'un ralentissement, mais de lui faire reconnaître des motifs connus dans des piles d'appels réelles.

**Le pipeline agentique de profiling.** Netflix a construit un système automatisé encadrant strictement le LLM. Une leçon clé a porté sur le cadrage : fournie sans limites, une trace brute complète pousse le modèle à gaspiller du raisonnement sur des détails hors de portée du développeur applicatif (pauses de garbage collection de la JVM, appels système du noyau Linux, overhead de frameworks tiers). Netflix impose donc des règles strictes de préfixes de paquets afin que l'agent ignore le bruit de la plateforme et se concentre uniquement sur le code applicatif propre à l'équipe.

**Les problèmes trouvés en production.** Le déploiement du pipeline a révélé quatre grandes catégories de bugs de performance :
1. *Goulot algorithmique* : une agrégation par Java Streams reconstruisait une map immuable à chaque étape de réduction (`putAll` recopiant systématiquement toutes les entrées existantes), entraînant une complexité quadratique et 8,8 % de CPU gaspillé. L'agent a remplacé cette réduction par une collecte en une seule passe (`flatMap` + `collect(toMap(...))`), de complexité linéaire.
2. *Regex sur le chemin critique* : une sanitation de chaînes de requête utilisait une substitution par expression régulière à chaque appel (`replaceAll`), consommant 46 % du CPU du service en raison du coût du parsing et des transitions d'automate. L'agent l'a remplacée par une table de correspondance précalculée indexée par caractère, avec un gain de performance d'un facteur 22.
3. *Allocation d'objets inutile provoquant des OOM* : un service créait un nouveau `HashSet` à chaque appel entrant pour vérifier la présence de champs de métadonnées, alors qu'une méthode de recherche interne existait déjà sur l'objet de données. L'instanciation répétée de ces objets consommait 47 % des collections du tas. L'agent a supprimé ces instanciations redondantes au profit de la méthode déjà disponible.
4. *Mauvais usage de librairie* : un service relookait une instance de compteur depuis un registre de métriques à chaque appel (`Metrics.counter(...).increment()`), ce qui impliquait des recherches en dictionnaire et des verrous de synchronisation internes — consommant 66 % du CPU contre seulement 0,3 % pour la logique métier réelle. L'agent a résolu le problème en mettant en cache la référence du compteur dès l'initialisation de la classe, et a détecté le même défaut dans trois services indépendants.

**Sécurité, vérification et architecture de confiance.** Laisser un agent modifier du code sans vérification automatique serait dangereux : une régression silencieuse serait pire qu'un code simplement inefficace. Le pipeline suit donc un cycle de développement logiciel classique en quatre étapes : (1) vérification logique — la branche de l'agent doit passer tous les tests unitaires, d'intégration et de contrat existants ; (2) déploiement canari — une instance canari reçoit une partie du trafic réel et s'exécute en parallèle d'une instance de référence identique ; (3) rapport d'observabilité — collecte de métriques de télémétrie dures (utilisation CPU relative, latence médiane, latence P99, taux d'allocation mémoire) sur une fenêtre suffisante, sans recours à un modèle IA pour juger les résultats ; (4) décision finale humaine — si le canari montre une amélioration nette sans hausse du taux d'erreur, le système ouvre une pull request contenant le changement de code, le flame graph original et le rapport canari, la décision de déploiement final restant entre les mains d'un développeur humain.

**Le déplacement vers l'amont (« shifting left »).** Le profiling automatisé en production reste limité : les anti-patterns ne sont détectés qu'après avoir déjà coûté des jours ou semaines de calcul gaspillé ; les développeurs hésitent naturellement à modifier un service qui fonctionne déjà en production ; et plusieurs équipes répètent souvent les mêmes erreurs, ce qui rend inefficace de relancer un agent coûteux sur chaque service séparément. Ces limites ont poussé Netflix à déplacer les vérifications de performance plus tôt dans le cycle de développement et à partager les découvertes à l'échelle de toute l'organisation. Comme les LLM sont sans état (chaque prompt démarre sans mémoire des découvertes précédentes), Netflix a construit un « Pattern Catalog » pour apporter une persistance partagée à travers la flotte de services. Ce catalogue repose sur quatre principes : être centralisé comme source unique de vérité pour toutes les équipes ; fonctionner de manière identique dans différents contextes (profiling hors ligne, vérifications CI/CD sur pull request, outils de développement locaux) ; être formaté pour être facilement injecté dans le prompt système d'un LLM par un script d'automatisation ; et rester lisible et révisable par des développeurs humains. Concrètement, Netflix a opté pour un simple dépôt Git de fichiers Markdown — sans base vectorielle ni infrastructure de recherche complexe —, une idée inspirée du concept de « wiki pour LLM » popularisé par Andrej Karpathy. Cette approche permet de diffuser les changements, d'ouvrir des pull requests, de retracer l'historique via Git, de scaler à des centaines de règles sans infrastructure de recherche dédiée, et de garder un format lisible aussi bien par des humains que par des modèles de langage.

**Comment Netflix détecte les problèmes en amont.** Grâce au Pattern Catalog, Netflix combine deux approches. La voie réactive : le système profile les services de production selon un calendrier récurrent ou à la demande ; quand l'agent trouve un nouveau goulot, il teste le correctif sur une instance canari puis, si tout va bien, fusionne le patch et documente la découverte dans le catalogue. La voie proactive : dès qu'un développeur ouvre une pull request, l'outillage CI effectue une recherche rapide (regex ou correspondance de symboles) dans l'index du Pattern Catalog ; si le code correspond à un anti-pattern connu, un bot CI interroge un LLM avec le diff de la pull request, qui laisse un commentaire en ligne expliquant l'inefficacité, son impact en ressources et un correctif suggéré — tout cela avant que le code ne soit fusionné dans la branche principale.

**Conclusion — une grille de maturité en quatre niveaux.** L'enseignement principal de l'expérience Netflix est que l'automatisation du performance engineering n'est pas un choix binaire, mais un spectre de maturité : le niveau 0 est entièrement manuel (les développeurs capturent eux-mêmes les traces et analysent les flame graphs) ; le niveau 1, dit « assisté », voit le LLM agir comme copilote analytique — le développeur lance le profiling mais confie l'analyse de la pile d'appels au modèle ; le niveau 2, dit « orchestration », correspond à l'état actuel de Netflix, avec un scan proactif généralisé et l'usage du Pattern Catalog ; le niveau 3, pleinement autonome, est la vision à long terme de Netflix, où les agents élaboreraient eux-mêmes des stratégies d'optimisation, exploreraient plusieurs implémentations alternatives et exécuteraient des benchmarks automatisés.

## Pourquoi ça compte

Ce cas illustre une tendance de fond en ingénierie logicielle : à mesure que l'IA générative accélère la production de code, l'automatisation doit aussi s'étendre à sa vérification et son optimisation — ici via des agents IA encadrés par des garde-fous stricts (tests, canari, revue humaine) plutôt que des correctifs appliqués en autonomie totale.
