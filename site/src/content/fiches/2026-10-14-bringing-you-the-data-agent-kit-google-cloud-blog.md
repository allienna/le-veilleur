## Résumé
Google Cloud présente le Data Agent Kit, un ensemble d'outils (plugin pour agents de code et extension pour IDE basés sur VS Code, dont l'IDE Antigravity) qui permet de construire un pipeline de données complet en dialoguant avec un agent plutôt qu'en codant manuellement chaque étape. L'article illustre ce fonctionnement via un cas d'usage concret : repérer des transactions de paiement potentiellement frauduleuses en partant de journaux bruts, jusqu'à une file de révision alimentée automatiquement chaque jour. Le kit combine des outils MCP connectant l'agent aux services de données Google Cloud et des "Skills" (fichiers Markdown de bonnes pratiques), tout en donnant accès depuis l'éditeur à des opérations comme l'interrogation de bases de données ou le déploiement de pipelines Airflow. Au final, l'exemple aboutit à un pipeline orchestré par Apache Airflow qui tourne quotidiennement sans intervention manuelle.

## Points clés
- Le Data Agent Kit ajoute deux capacités : des outils MCP qui relient l'agent aux services de données Google Cloud, et des "Skills" en Markdown qui lui fournissent instructions et bonnes pratiques propres à la stack de données.
- Le scénario démonstratif suit un data scientist qui doit, à la demande de l'équipe conformité, prioriser des transactions suspectes de fraude.
- Le pipeline complet enchaîne : ingestion de journaux JSON depuis Cloud Storage vers BigQuery via un notebook Spark Serverless généré par l'agent, nettoyage/déduplication/enrichissement via un projet dbt, entraînement d'un classifieur Random Forest sur Spark, puis scoring des transactions non labellisées.
- Les transactions dont la probabilité de fraude estimée dépasse 50 % sont envoyées vers une file de révision stockée dans Spanner, consultable directement depuis l'IDE.
- L'automatisation finale repose sur le Managed Service for Apache Airflow : l'agent génère la définition YAML du pipeline (planification, dépendances) et la configuration de déploiement, puis la convertit en DAG Airflow visualisable et exécutable comme un graphe interactif dans l'IDE.
- Google propose pour approfondir un codelab guidé, une documentation dédiée, ainsi qu'un dépôt GitHub open source regroupant les "Skills" et outils du kit.

## Analyse approfondie
**Le scénario de départ.** L'article part d'un cas concret : l'équipe conformité constate que certains paiements tardent à se régler et suspecte des cas de fraude. Le data scientist doit produire une liste priorisée de transactions à examiner. Pour y arriver, il faut ingérer et nettoyer des journaux de transactions bruts, entraîner un modèle sur les fraudes passées, noter les nouvelles transactions, puis planifier l'exécution quotidienne de l'ensemble du pipeline. L'article déroule la construction de ce workflow de bout en bout avec un agent, en utilisant le Data Agent Kit directement dans l'IDE Antigravity.

**Présentation du Data Agent Kit.** Le kit se présente sous forme d'un plugin pour agents de codage ou d'une extension pour IDE de la famille VS Code, destiné à faciliter le travail avec les données hébergées sur Google Cloud. Il apporte deux ajouts majeurs au workflow : d'une part, une assistance pour l'agent lui-même, via des outils MCP qui le connectent aux services de données, et des "Skills" — des fichiers Markdown qui lui donnent des instructions et des bonnes pratiques adaptées à la pile de données utilisée ; d'autre part, des outils directement intégrés à l'IDE, permettant d'interagir avec le Agentic Data Cloud de Google — interroger des bases, déployer un pipeline Airflow — sans quitter l'éditeur.

**Chargement des données.** Le point de départ, ce sont les journaux de transactions bruts stockés dans Google Cloud Storage. L'utilisateur demande simplement à l'agent de créer un notebook chargeant ces journaux dans BigQuery via Spark. L'agent génère alors un notebook Jupyter qui charge les journaux au format JSON dans une table BigQuery nommée raw_transactions. Ce notebook peut être relu, vérifié puis exécuté depuis l'IDE grâce à un environnement Spark Serverless préconfiguré. Une fois l'exécution terminée, la table raw_transactions peut être explorée directement avec le Data Agent Kit, qui permet de parcourir son contenu et d'en inspecter les métadonnées sans sortir de l'éditeur. À ce stade, les données sont dans BigQuery mais pas encore exploitables pour l'entraînement d'un modèle : il reste à éliminer les doublons et enregistrements incomplets, puis à enrichir chaque transaction avec les informations sur l'expéditeur et le destinataire du paiement.

**Nettoyage des données.** Pour rendre cette logique de nettoyage réutilisable à chaque nouveau lot de données, elle est encapsulée dans un projet dbt, avec un test garantissant qu'une transaction n'apparaît qu'une seule fois. Sur simple demande à l'agent, celui-ci génère un projet dbt complet, avec des modèles SQL gérant à la fois le nettoyage et l'enrichissement des données par jointure avec les tables de référence. Après relecture du code généré — notamment la gestion des doublons et des jointures — l'utilisateur exécute dbt build depuis le terminal intégré. Cette commande construit les tables de staging et les tables enrichies dans BigQuery, ainsi qu'une table séparée regroupant les enregistrements dont l'identifiant de transaction est manquant ; le test d'unicité est également exécuté à cette occasion. La colonne is_fraud, indiquant si une transaction passée était frauduleuse, est conservée : c'est elle qui servira à entraîner le modèle sur les cas connus, avant de l'utiliser pour noter les transactions dont le statut frauduleux reste inconnu.

**Construction de la file de révision.** Les données étant prêtes, l'étape suivante consiste à demander à l'agent de créer un notebook d'entraînement s'appuyant sur un classifieur de type Random Forest exécuté sur Spark Serverless. Une fois le notebook relu et exécuté, l'utilisateur peut consulter ses métriques d'évaluation pour juger de la capacité du modèle à distinguer les transactions frauduleuses des transactions légitimes. L'extension Data Agent Kit permet aussi de vérifier que les artefacts du modèle entraîné ont bien été sauvegardés dans Google Cloud Storage. Le modèle sauvegardé est ensuite utilisé pour noter les transactions ne disposant pas encore de valeur is_fraud : dans l'exemple, le notebook d'inférence attribue un score aux transactions non labellisées dans BigQuery, et envoie celles dont la probabilité de fraude estimée atteint au moins 50 % vers la file de révision stockée dans Spanner. Ces transactions signalées aident l'équipe à prioriser ses investigations, sans pour autant trancher elles-mêmes sur l'existence d'une fraude. En observant comment le notebook d'inférence filtre et écrit les enregistrements signalés, puis en l'exécutant, l'utilisateur peut ensuite interroger la table Spanner depuis l'IDE pour inspecter les résultats. Cette table constitue précisément la liste recherchée au départ : l'équipe conformité peut désormais commencer ses revues, et l'ensemble du trajet — des journaux bruts jusqu'à la file de révision — est opérationnel.

**Automatisation de l'exécution quotidienne.** Jusqu'ici, chaque étape a été lancée manuellement. L'étape suivante consiste à les enchaîner pour que le workflow s'exécute automatiquement chaque jour : chargement des derniers journaux, application des transformations dbt, puis scoring des transactions non labellisées à l'aide du modèle sauvegardé. Ces étapes sont orchestrées via le Managed Service for Apache Airflow de Google Cloud. Sur demande, l'agent génère une définition de pipeline au format YAML ainsi qu'une configuration de déploiement : la définition fixe la planification et les dépendances entre les étapes, tandis que la configuration de déploiement précise l'environnement Airflow dans lequel le pipeline s'exécutera. Le Data Agent Kit transforme ensuite cette définition en un DAG Airflow, explorable sous forme de graphe interactif dans l'IDE, en ouvrant le pipeline sous la section "Orchestration Pipelines" ; cliquer sur une tâche permet de l'inspecter, et pour les tâches de type notebook, un lien renvoie directement au code correspondant. Une fois l'environnement Airflow configuré, un clic sur "Run pipeline" dans le canevas déclenche l'ensemble du processus : le Data Agent Kit empaquette les notebooks et le projet dbt, déploie le DAG et lance son exécution. L'historique d'exécution du pipeline permet de suivre sa progression, et chaque tâche individuelle peut être inspectée (statut, durée, logs). Grâce à cette automatisation, Airflow exécute le pipeline chaque jour, faisant transiter de nouveaux lots de données depuis les journaux bruts jusqu'à la file de révision, ce qui permet à l'équipe conformité de se concentrer sur les transactions signalées pendant que le reste du travail est automatisé.

**Pour aller plus loin.** Google met à disposition un codelab détaillant la mise en place complète de ce workflow, ainsi qu'une documentation dédiée et un dépôt GitHub open source regroupant les Skills et outils présentés.

## Pourquoi ça compte
Cet article illustre une tendance de fond en ingénierie des données : le passage d'un code écrit manuellement à des pipelines entiers (ingestion, nettoyage dbt, ML, orchestration Airflow) générés et pilotés par un agent conversationnel directement dans l'IDE, ce qui pourrait fortement réduire le temps de mise en production de workflows data/ML standards tout en gardant un contrôle humain sur le code généré.
