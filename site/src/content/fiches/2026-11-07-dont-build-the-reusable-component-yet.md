## Résumé
L'article argumente contre le réflexe consistant à créer immédiatement un composant réutilisable dès que deux écrans se ressemblent. L'auteur raconte avoir fusionné trois workflows distincts (approbation, modification, déplacement d'un item) dans un seul composant « ItemAction », pensant économiser du code — pour finir avec un empilement de flags, modes et cas spéciaux rendant toute modification coûteuse et politiquement complexe. La thèse centrale, inspirée de la « règle de trois » (Don Roberts/Martin Fowler) et de Sandi Metz (« The Wrong Abstraction »), est qu'une duplication de code coûte toujours moins cher à défaire qu'une mauvaise abstraction. L'auteur propose un test simple pour distinguer vraie duplication et simple coïncidence visuelle, ainsi qu'une méthode pour « désabstraire » un composant prématurément généralisé.

## Points clés
- Deux bouts de code identiques en apparence ne partagent pas forcément la même « raison de changer » — c'est ce critère, et non la ressemblance visuelle, qui justifie une abstraction commune.
- Fusionner trop tôt trois workflows (ici : approbation, modification, déplacement d'un item) dans un seul composant a produit une accumulation de flags (`mode`, `variant`, `showDetails`, `onSpecialCase`) et de branches conditionnelles, rendant chaque futur changement sujet à l'accord de tous les propriétaires concernés.
- La règle de trois (attribuée à Don Roberts via Fowler) : on tolère la duplication la première fois, on grimace la deuxième, on refactore seulement à la troisième occurrence partageant la même cause de changement.
- Certains éléments méritent d'être partagés dès le premier jour : composants primitifs stables (boutons, inputs), design tokens, comportements d'accessibilité, et tout ce qui est dicté par un standard externe (dates, devises, protocoles).
- Un bon indicateur de dérive : si les props d'un composant décrivent *ce qu'il faut afficher* (children, size, tone), l'abstraction est saine ; si elles décrivent *dans quelle situation on se trouve* (mode, variant, isSpecial), plusieurs logiques distinctes ont probablement été fusionnées à tort.
- Pour corriger une abstraction prématurée : réintégrer (« inline ») le code commun dans chaque site d'appel, le simplifier localement, laisser les workflows diverger, puis n'extraire à nouveau que les fragments réellement communs (ex. un formateur de date) une fois le code stabilisé.

## Analyse approfondie
L'auteur part d'un constat familier à quiconque a travaillé en frontend : la pression culturelle pousse presque toujours vers la factorisation et la création de composants « DRY ». Il propose de nuancer ce réflexe à travers un cas concret vécu : trois workflows distincts (approuver un item, modifier ses paramètres, le déplacer entre zones gérées) partageaient la même structure d'interface — liste, sélection, confirmation, retour visuel (toast/pop-up). Séduit par cette ressemblance de surface, il a fusionné les trois dans un unique composant `ItemAction`.

Le problème, identifié rétrospectivement, est que la ressemblance n'était qu'apparente : chacun des trois processus gère différemment les échecs partiels, a ses propres exigences métier et ses propres besoins d'audit. L'approbation est un engagement sur l'avenir, la modification est immédiate, et le déplacement dépend de l'acceptation d'un système tiers pouvant le refuser.

L'article illustre la dégradation du composant unique au fil des semaines : ce qui n'était qu'un objet `Item` simple est devenu une interface `ItemActionProps` chargée de champs optionnels (`mode`, `variant`, `showDetails`, `requireReason`, `onSpecialCase`), avec une logique interne truffée de branches spécifiques à un seul mode (par exemple un cas spécial ne concernant que les déplacements). Chaque nouvel ajout était individuellement justifié, mais leur accumulation a fini par exiger l'accord de tous les propriétaires de workflow avant toute modification, ainsi que des tests couvrant toutes les combinaisons possibles de mode et de variante. Un changement local se transformait systématiquement en négociation collective.

L'auteur explique ensuite *pourquoi* ce piège est si fréquent : réduire le nombre de lignes de code procure une satisfaction immédiate et visible (un diff négatif impressionnant), et la cohérence visuelle semble a priori une bonne pratique de conception. Mais cette décision ne s'appuie que sur l'état présent du code : les similitudes sont observables immédiatement, alors que les différences futures — nouvelle politique, nouvelle exigence d'audit, nouvelle intégration imprévue — ne se révèlent que plus tard. Autrement dit, l'abstraction capture ce que le code a en commun aujourd'hui, mais toute divergence future n'aura d'autre choix que de se traduire par un flag supplémentaire.

Il formule alors sa règle pratique : attendre qu'un même motif se répète trois fois pour la même raison avant de factoriser, et dans l'intervalle laisser chaque écran évoluer indépendamment, même si cela duplique du code. Le point clé, selon lui, est de définir précisément ce qu'est une « même raison de changer » : deux fragments de code partagent une même cause de changement si une seule décision, prise par une seule personne, les fait évoluer simultanément. Il illustre la distinction avec deux exemples : une fonction de formatage de date utilisée par trois écrans constitue une vraie duplication (un changement de format d'affichage doit se répercuter partout), alors que deux appels API qui se ressemblent syntaxiquement (`api.post("/approve", ...)` vs `api.post("/change", ...)`, suivis chacun d'un toast de succès) relèvent en réalité de décisions indépendantes — l'un lié à la politique d'approbation, l'autre aux règles de validation — et ne devraient donc pas être fusionnés malgré leur ressemblance.

Son test pratique : « Si cette exigence changeait, qui consulterais-je, et toutes les copies du code changeraient-elles en même temps ? » Si la réponse diffère selon la copie considérée, il s'agit d'une coïncidence de code, non d'une duplication à éliminer. Il relie cette idée à des références bien connues du génie logiciel : la « règle de trois » attribuée à Don Roberts et popularisée par Martin Fowler dans *Refactoring*, l'essai « The Wrong Abstraction » de Sandi Metz (qui affirme que la duplication coûte moins cher que la mauvaise abstraction), et le principe AHA (« Avoid Hasty Abstractions ») de Kent C. Dodds.

L'auteur précise ensuite que sa position n'est pas un rejet total de la réutilisation : certains éléments méritent d'être partagés dès le premier jour. Il cite quatre catégories : les primitives d'interface stables et peu chargées de logique métier (boutons, champs de texte, conteneurs de mise en page) ; les design tokens (couleurs, espacements, échelles typographiques), dont la vocation même est d'être utilisés partout ; les comportements d'accessibilité (piégeage du focus dans les dialogues, navigation au clavier, étiquetage), qu'il vaut mieux implémenter correctement une seule fois plutôt que de risquer des erreurs répétées ; et tout ce qui est dicté par un standard externe (dates, devises, clients de protocole), dont la forme est définie ailleurs et donc peu susceptible d'être déformée par les besoins futurs d'un écran particulier.

Il propose trois critères pour juger si une abstraction est légitime : la forme est-elle déterminée par autre chose que des spéculations sur l'avenir ? Existe-t-il une seule raison de la faire évoluer ? S'agit-il d'un composant d'affichage ou d'un workflow métier ? Son test olfactif favori reste l'examen de la liste des props : si elles décrivent ce qui doit être rendu visuellement (children, size, tone), l'abstraction est probablement saine ; si elles décrivent plutôt un contexte d'usage (mode, variant, isSpecial), plusieurs logiques distinctes ont vraisemblablement été combinées à tort.

Enfin, l'article détaille la méthode de récupération d'une abstraction prématurée. Première étape : réintégrer (« inliner ») le module partagé dans chaque site d'appel, en copiant son code dans chaque workflow et en supprimant les branches que ce workflow particulier n'utilise jamais. Cette démarche semble régressive, mais elle redonne à chaque copie une forme courte et compréhensible, et permet à chaque workflow d'évoluer sans nécessiter l'accord des autres équipes. Deuxième étape : organiser le code par workflow plutôt que par type d'interface visuelle. Une fois les trois implémentations stabilisées séparément, il devient possible d'identifier ce qui est réellement commun pour les mêmes raisons (par exemple un composant de table ou un formateur de date) et de n'extraire que ces fragments précis — une démarche également recommandée par Sandi Metz dans son essai.

L'auteur conclut en résumant sa règle : copier-coller jusqu'à ce qu'un même motif apparaisse trois fois pour la même raison, sauf lorsqu'il s'agit d'emblée de primitives, de tokens, d'accessibilité ou de standards externes — qu'il convient alors de factoriser immédiatement. Il termine en invitant le lecteur à s'interroger sur le code que son équipe évite de toucher par peur de le casser, et sur les flags spéciaux qu'elle a dû introduire pour un appelant particulier.

## Pourquoi ça compte
Ce texte offre un contre-argument utile et bien structuré à l'orthodoxie DRY dominante en développement frontend, avec un critère concret (« même raison de changer ») directement applicable lors des revues de code et des décisions d'architecture au quotidien.
