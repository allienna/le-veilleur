## Résumé

GitHub Actions prend désormais en charge les fichiers de verrouillage (lockfiles) pour les workflows, une nouvelle défense contre les attaques de la chaîne d'approvisionnement logicielle. Jusqu'ici, la bonne pratique consistait à épingler chaque action sur son SHA complet plutôt que sur un tag, car les tags sont mutables et peuvent être redirigés par un attaquant vers du code malveillant. L'auteur détaille l'installation de l'extension `gh-actions-lock` pour le CLI `gh`, la génération et la validation en CI du lockfile, ainsi que l'intégration de zizmor, un linter de sécurité pour GitHub Actions qui supporte désormais lui aussi ces lockfiles. Renovate et Dependabot prennent déjà en charge la mise à jour automatique de ces fichiers.

## Points clés

- Les lockfiles de GitHub Actions remplacent l'épinglage par SHA complet comme défense recommandée contre la mutabilité des tags et les attaques de supply chain.
- Installation simple via `gh extension install github/gh-actions-lock`, puis génération du lockfile avec `gh actions-lock`.
- Les workflows peuvent garder des tags lisibles (`vX.Y.Z`) tandis que le lockfile `.github/workflows/actions.lock` enregistre le SHA résolu correspondant.
- La CI doit exécuter `gh actions-lock --verify` dans un job dédié pour détecter un lockfile obsolète ou corrompu.
- Renovate et Dependabot savent déjà mettre à jour les lockfiles automatiquement ; penser à utiliser des cooldowns.
- zizmor (linter de sécurité pour GitHub Actions), fortement recommandé, supporte les lockfiles depuis la version v1.32.0.

## Analyse approfondie

GitHub Actions prend désormais en charge les lockfiles de workflow.

Parce que les GitHub Actions sont récupérées depuis Git, la recommandation précédente était de les épingler sur un SHA complet plutôt que sur un tag. En effet, les tags sont mutables et vulnérables à des attaques de la chaîne d'approvisionnement où un attaquant pointe un tag auparavant sûr vers du code malveillant.

Par exemple, un ancien workflow ressemble à ceci :

```
name: Lint
on: [push, pull_request, workflow_dispatch]
permissions: {}
env:
  FORCE_COLOR: 1
  RUFF_OUTPUT_FORMAT: github
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: j178/prek-action@44924fe9ef4a6f88253c4b6b1bf11c689d3ce53d # v3.1.0
```

Voici comment j'ai mis en place les lockfiles.

### Installation

Installez l'extension `gh-actions-lock` pour le CLI `gh` :

```
$ gh extension install github/gh-actions-lock
✓ Installed extension github/gh-actions-lock
```

### Verrouillez-les

Dans votre dépôt, lancez :

```
$ gh actions-lock
✓ All 1 workflows valid
```

Le workflow utilise désormais des tags `vX.Y.Z` et ressemble à ceci :

```
diff --git a/.github/workflows/lint.yml b/.github/workflows/lint.yml
index 946971c..3503607 100644
--- a/.github/workflows/lint.yml
+++ b/.github/workflows/lint.yml
@@ -13,7 +13,7 @@ jobs:
     runs-on: ubuntu-latest
     steps:
-      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
+      - uses: actions/checkout@v7.0.1
         with:
           persist-credentials: false
-      - uses: j178/prek-action@44924fe9ef4a6f88253c4b6b1bf11c689d3ce53d # v3.1.0
+      - uses: j178/prek-action@v3.1.0
```

Et cela génère un lockfile à l'emplacement `.github/workflows/actions.lock` :

```
# This file is machine-generated by `gh actions-lock`.
# Do not edit by hand; run `gh actions-lock` to update.
# Docs: https://gh.io/actions-lockfile
version: 'v0.0.3'
workflows:
    '.github/workflows/lint.yml':
        - 'actions/checkout@v7.0.1'
        - 'j178/prek-action@v3.1.0'
dependencies:
    'actions/checkout@v7.0.1':
        ref: 'v7.0.1'
        commit: 'sha1-3d3c42e5aac5ba805825da76410c181273ba90b1'
        owner_id: 44036562
        repo_id: 197814629
    'j178/prek-action@v3.1.0':
        ref: 'v3.1.0'
        commit: 'sha1-44924fe9ef4a6f88253c4b6b1bf11c689d3ce53d'
        owner_id: 10510431
        repo_id: 1052387486
```

Commitez les workflows modifiés ainsi que le nouveau lockfile.

### Renovate et Dependabot

Bonne nouvelle, les deux outils supportent déjà les lockfiles ! Vos mises à jour périodiques mettront aussi à jour le lockfile. N'oubliez pas d'utiliser des cooldowns.

### Validation

GitHub recommande également de vérifier les lockfiles en CI pour s'assurer qu'ils sont à jour et non corrompus.

Ils suggèrent de copier ce fichier `verify-lockfile.yml` dans votre dépôt. J'ai choisi de l'intégrer à mon workflow de lint existant, mais dans son propre job afin qu'il s'exécute indépendamment et en parallèle :

```
name: Lint
on: [push, pull_request, workflow_dispatch]
permissions: {}
env:
  FORCE_COLOR: 1
  RUFF_OUTPUT_FORMAT: github
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7.0.1
        with:
          persist-credentials: false
      - uses: j178/prek-action@v3.1.0
  # Fails when .github/workflows/actions.lock is out of sync with the
  # workflows or a locked pin no longer verifies upstream.
  lockfile:
    runs-on: ubuntu-slim
    env:
      GH_TOKEN: ${{ github.token }}
    steps:
      - uses: actions/checkout@v7.0.1
        with:
          persist-credentials: false
      - run: gh extension install github/gh-actions-lock --pin v0.4.1
      - run: gh actions-lock --verify
```

Notez que j'utilise ici le runner léger `ubuntu-slim`. Notez aussi que l'épinglage se fait sur la version v0.4.1 ; il faudra la mettre à jour à un moment donné, ou trouver un moyen de l'automatiser. Ce sera pour une prochaine fois.

N'oubliez pas qu'on vient de modifier les actions d'un workflow, il faut donc relancer `gh actions-lock` pour reverrouiller. Rien ne change réellement pour `lint.yml` puisqu'il verrouillait déjà `actions/checkout`. Mais si vous créez un nouveau fichier comme `verify-lockfile.yml`, il faudra reverrouiller pour celui-ci. La CI vous le signalera.

### zizmor

zizmor est un linter de sécurité pour GitHub Actions, et il est **fortement recommandé**. Si vous ne l'utilisez pas encore, faites-le.

Les versions antérieures à v1.32.0 recommandaient d'épingler les actions par hash, et v1.32.0 est la première version à supporter les lockfiles.

J'utilise zizmor via prek, donc ajoutez ou mettez à jour zizmor dans `.pre-commit-config.yaml` :

```
  - repo: https://github.com/zizmorcore/zizmor-pre-commit
    rev: v1.32.0
    hooks:
      - id: zizmor
```

## Pourquoi ça compte

Cet article documente un changement concret et actionnable dans la sécurisation des pipelines CI/CD : les lockfiles de GitHub Actions simplifient la défense contre les attaques de supply chain sans sacrifier la lisibilité des workflows, un sujet pertinent pour toute équipe suivant les évolutions de la sécurité DevOps.
